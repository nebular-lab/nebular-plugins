# テストケースの漏れチェックのプロンプト

生成したテストコードに、設計書から作るはずのケースが漏れていないか、設計書にないケースが紛れていないかを、サブエージェントに確かめさせるためのプロンプト。書いた本人は自分の思い込みに引きずられて見落としやすいので、別のエージェントに読ませる。

## 使い方

1. 下の「プロンプト」の `{...}` を埋める。
2. Agent ツールで汎用のサブエージェントを起動し、埋めたプロンプトを渡す。完了を待つ。
3. 返ってきた「漏れ」「誤り」を直す。直したら、もう一度 1〜3 を行う。チェックは最大 3 回までにし、3 回目でも残ったものは直さずに、報告でユーザーに伝える。「確認」はユーザーに伝える。

## プロンプト

````text
あなたはテスト設計のレビュアーです。次のファイルを読み、テストコードが「テストケースの作り方」の規則どおりに、設計書からケースを洗い出せているかを確かめてください。ファイルは編集しないでください。

- 画面設計書: {SCR-NNN_<slug>.md の絶対パス}
- ワイヤーフレーム: {SCR-NNN_<slug>.html の絶対パス}
- OpenAPI 定義: {パス。なければ「なし」}
- テストコード: {SCR-NNN_<slug>.spec.ts の絶対パス}
- テストケースの作り方: {write-screen-e2e/references/test-case-rules.md の絶対パス}
- メッセージ一覧: {messages.md の絶対パス}
- 共通ルール: {common-rules.md の絶対パス}
- 画面設計書の記述規則: {write-screen-spec/references/writing-rules.md の絶対パス}（設計書に書かれない暗黙の振る舞い、たとえば「表示していない項目と編集不可の項目はチェックしない」を知るために読む）

最初に「テストケースの作り方」と「画面設計書の記述規則」を全部読んでください。次に、設計書を上から読み、規則に従えば作るはずのケースを自分で一覧にしてから、テストコードの test() / test.fixme() と 1 つずつ突き合わせてください。ループで生成しているテストは、配列を展開して数えてください。

## 確かめること
1. 漏れ: 規則に従えば作るはずなのに、テストコードにないケース。特に次を確かめる。
   - 初期表示とアクションのレスポンスの表の全行（「上記以外」を含む）、リクエストの表（条件付きで送る・送らないパラメータを含む）
   - バリデーションのチェック表の全行と、境目の値（ちょうど・超える）
   - 表示条件・活性条件・編集不可条件・省略表記・文言が変わる条件の、満たす場合と満たさない場合
   - API を呼ばない手順（表示の切り替え、ダイアログの開閉など）の各手順と、「なら／なければ」の両方
   - 入力可能文字種・入力可能最大文字数が `-` でない項目ごとのケースと、備考・共通ルールに書かれた振る舞い（変換、貼り付けなど）
   - クエリパラメータ（値を付けたとき・省略したとき）、クエリパラメータを書き換える手順の URL と履歴の扱い（追加・置き換え）、document.title、初期フォーカス、Enter キーで動くボタン（`-` 以外のとき）、備考の読み上げ名、初期値（新規・編集などの書き分けごと）、プレースホルダー、エラー表示（初期表示ではどれも出ていないことを、画面で 1 ケース）
   - エラー表示が非表示に戻る側。設計書の「〜を非表示にする」手順（バリデーションで違反がなくなったとき、次の送信で画面上部のエラーを消すとき、入力項目を非表示にするとき）ごと、エラー表示ごとに、先にエラーを出してから消えることを確かめるケースがあるか
   - 同じ項目にチェック表の行が 2 つ以上あるチェック表ごとの優先順位のケース（送信時にだけチェックする項目も含む）
   - 項目ごとのエラーの表示先の表（「422 の表示先」）の、`上記以外` に当たる field のケース
   - 共通ルールのアクセシビリティのルールごとのケース（入力項目のエラーの説明、読み上げでの通知の `test.fixme()`、送信時のエラーでのフォーカス、確認ダイアログごとのフォーカスと Esc キー、一覧の結果の通知、Tab キーの順序）
   - 確認ダイアログごとの、開く前に表示されていないケースと、中のボタンのアクションのケース
   - ボタン・リンクを押して遷移するアクションの全部（同一タブ・別タブ）と、確認ダイアログを経る遷移の 4 ケース
   - 権限の表の全行（ほかのケースで確かめているなら、その出典に併記されているか）
   - TBD の箇所が test.fixme() で置かれているか
2. 誤り: テストの中身が設計書と食い違っているもの。
   - 期待するメッセージの文言（メッセージ一覧の文言の変数に、設計書の参照で指定された値を入れたもの）、遷移先、ステータス、送るはずの値が設計書と違う
   - コメントの部品番号（`// No.9` など）が、ワイヤーフレームの今の番号と合っていない
   - テスト名の出典（[「下書き保存」ボタン押下（編集） / PUT /events/{eventId} 409] など）が、実際の設計書の手順・行を指していない
   - レスポンスの body やリクエストのパラメータ名が OpenAPI と合わない
   - 設計書に書いていない振る舞いを期待値にしている
   - 出典の形が規則の表と違う、1 つのテストで 2 つ以上のケースを確かめている
   - テスト名に設計書の ID（No.6、MSG-018、A5、手順番号、SCR-001）が入っている。項目名・メッセージの文言・操作名・画面名で書く
   - 入力可能文字種・入力可能最大文字数で入力できない値について、エラーを期待している（入力できないので、違反は起きない）
   - バリデーションの違反値・境目の値が、チェック表の「条件」の値と合っていない
   - 特定の属性（`role="alert"`、`aria-*`、`data-*`）や、ライブラリ固有の DOM の形を前提にした確かめ方をしている（ダイアログを `dialog` だけで探している、など）
   - 弱い検査: 起きるはずのことを待たずに「起きないこと」を確かめている、先にエラーを出さずに「エラーが表示されていない」を確かめている（画面で 1 件の `[エラー表示 表示条件]` を除く）、最初から画面内にある項目で toBeInViewport を確かめている、遷移先の URL のクエリを確かめていない
   - ファイルの先頭に実装についての前提が書かれていない、test.use で timezoneId と viewport を固定していない
3. 確認: 規則違反とは言い切れないが、ユーザーに確かめたほうがよいもの（設計書の記述があいまいで、テストの期待値を決めきれないものなど）。

## 報告の形
日本語で、次の形で報告してください。問題がなかった項目は「なし」と書いてください。

```
## 漏れ
- [設計書:行] 作るはずのケース（出典の形で）。どう書けばよいか。
## 誤り
- [テストコード:行] 何が食い違っているか。どう直せばよいか。
## 確認
- ...
## 数
- 設計書から洗い出したケース: N 件 / テストコードのケース: N 件（うち test.fixme: N 件）
```
````
