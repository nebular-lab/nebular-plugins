# テストケースの作り方

画面設計書（`.md`）とワイヤーフレーム（`.html`）から、Playwright のテストケースを機械的に洗い出すための規則。目的は「どのテストケースを作るか」を明確にすること。誰が作っても同じケースが並ぶように、設計書のどの記述から何のケースを作るかを決めておく。迷ったら [サンプル](../../../examples/e2e/screens/SCR-002_event-edit.spec.ts) に従う。

設計書の書き方は `write-screen-spec` の [writing-rules.md](../../write-screen-spec/references/writing-rules.md) で決まっている。設計書に書かれない暗黙の振る舞い（「表示していない項目と編集不可の項目はチェックしない」など）もそこにあるので、先に読む。

## 目次

- テスト名と出典
- 1. API を呼ぶ手順
- 2. API を呼ばない手順

- 部品の特定（ロケーター）
- メッセージ
- モック
- モーダルだけの画面
- ファイルの構成

## 対象と前提

**対象外**

- サーバー側で API を呼ぶ画面（SSR）。`page.route()` ではサーバー側の通信を横取りできないため。
- API のモックだけでは画面を開けない認証（クライアント側にトークンや Cookie が必要なもの）。

設計書やアプリからこれらに当たるとわかったら、ユーザーに伝えて止まる。

**実装についての前提**

テストが通るかどうかは、実装の細部にも左右される。次を前提にし、テストファイルの先頭のコメントにも書く。実装が前提と違うときは、テストを合わせるのではなく、設計書か実装を直すかをユーザーに相談する。

- API はブラウザから fetch か XHR で呼ぶ。
- 入力欄は、その見出し（設計書の `◯◯の見出し` の部品）と関連付けられている（`getByLabel` で特定できる）。まとめたラジオ・チェックボックスの見出しは、文言で特定する。
- アプリ内の確認ダイアログ・モーダルは、ダイアログとして見つかる（役割が `dialog` か `alertdialog` のどちらか）。
- 見出しは `heading` のロールを持つ。
- 特定の属性（`role`、`aria-*`、`data-*`）や、ライブラリ固有の DOM の形は前提にしない。部品は役割と名前で探し、アクセシビリティは「読み上げソフトにどう伝わるか」の結果（名前、説明、フォーカスの位置、キー操作）で確かめる。どのコンポーネントライブラリで実装しても、結果が同じなら通るようにするため。
- メッセージ（トーストを含む）は画面上のテキストとして 1 か所に表示される。トーストは、遷移したあとも確かめられる間は表示されている。
- 入力欄が受け付ける範囲は、設計書の「入力可能文字種」「入力可能最大文字数」と、共通ルール（`common-rules.md`）のとおりに実装されている。この 2 つの列が `-` の項目は、どの文字も何文字でも入力でき、違反はバリデーションでエラーになる（`maxlength` などで入力そのものを止めない）。

**テストの環境**

- バックエンドとは通信しない。API はすべて [api-mock.ts](../assets/api-mock.ts) でモックする。モックしていない API が呼ばれたら、そのテストは失敗する。
- `test.use()` で次を固定する。
  - `timezoneId: 'Asia/Tokyo'`（「今日」がタイムゾーンで変わらないようにする。設計書が別のタイムゾーンを前提にしていればそれに合わせる）
  - `viewport`: `{ width: 1280, height: 720 }`（画面は、すべて PC 表示の前提）
- 日付が関わる画面では、`page.clock.setFixedTime()` で「今日」を固定する。時刻は日中（`T12:00:00`）にする。

## テスト名と出典

テスト名だけを読めば、何を確かめるケースで、設計書のどこから来たかがわかるようにする。

```ts
test(`[「更新する」ボタン押下（編集） / PUT /events/{eventId} 409] 公開中の更新で 409 が返ると、${q(M.MSG018)}を表示する`, async ({ page, api }) => {
// → [「更新する」ボタン押下（編集） / PUT /events/{eventId} 409] 公開中の更新で 409 が返ると、「他の人が先に更新しました。…」を表示する
```

- テスト名には、設計書の ID（部品番号 `No.6`、メッセージ ID `MSG-018`、アクション ID `A5`、手順番号、画面 ID `SCR-001`）を使わない。読む人が設計書を開かなくてもわかるようにするため。
  - 部品は、画面項目の表の項目名で書く（`タイトル`、`「下書き保存」ボタン`）。
  - アクションは、アクション一覧の「操作」で書く（`「下書き保存」ボタン押下`）。「操作」に部品番号が入っていれば項目名に置き換える（`No.9 からフォーカスが外れる` → `タイトルからフォーカスが外れる`）。
  - メッセージは、文言をそのまま「」で書く。コードでは `M` 定数を `` `${q(M.MSG018)}` `` のように埋め込む（`q` は「」で囲む関数）。変数のある文言は、テストで使う値を入れた文言にする。
  - 他の画面は、画面名で書く（`イベント一覧へ遷移する`）。
- 先頭の `[...]` が出典。形は下の表のとおり。
- 続けて「条件」と「期待する結果」を 1 文で書く。「〜すると〜する」「〜のとき〜する」の形。
- 1 つのテストで確かめるのは 1 つのケース。満たす場合と満たさない場合、2 つの項目、2 つの制約は、別々のテストにする。
- テスト名は画面の中で重複させない（Playwright は同じ名前のテストをエラーにする）。
- 似たケースが並ぶときは、ケースの配列を作ってループで `test()` を生成する。配列そのものがケースの一覧になり、読みやすいため。

| 分類 | 出典の形 | 例 |
| --- | --- | --- |
| API のリクエスト | `[場面 / メソッド パス リクエスト]` | `[「下書き保存」ボタン押下（新規作成） / POST /events リクエスト]`、`[… / POST /events リクエスト（概要あり）]` |
| API のレスポンス | `[場面 / メソッド パス ステータス]` | `[初期表示 / GET /events/{eventId} 404]`、`[削除の確認で「削除する」ボタン押下 / DELETE /events/{eventId} 上記以外]` |
| 状態の切り替え | `[場面 / 状態名]` | `[「下書き保存」ボタン押下 / 保存中]`、`[初期表示 / 読み込み中]` |
| API を呼ばない手順 | `[場面]`、条件があれば `[場面 / 条件]` | `[「削除」ボタン押下]`、`[開催形式の選択を変更 / 「会場」を選んだとき]` |
| バリデーション | `[項目名 条件]`（条件は、チェック表の「条件」をそのまま。長いものは先頭の語だけ）、違反しない境目は `[項目名 条件 境目]` | `[タイトル 50 文字以内]`、`[タイトル 50 文字以内 境目]`、`[タイトル 使える文字]` |
| バリデーションの付随 | `[項目名 内容]`、`[場面 / 内容]` | `[タイトル エラーの消去]`、`[「下書き保存」ボタン押下 / 画面上部のエラーの消去]`、`[タイトル 優先順位]`、`[「下書き保存」ボタン押下 / タイトルのバリデーション]`、`[「更新する」ボタン押下 / 編集不可の項目]`、`[「下書き保存」ボタン押下 / スクロール]` |
| 入力できる範囲 | `[項目名 入力可能文字種]`、`[項目名 入力可能最大文字数]` | `[定員 入力可能最大文字数]` |
| 共通ルール | `[共通ルール 項目の名前 / 入力項目の項目名]` | `[共通ルール 送信時に前後の空白を取り除くか / タイトル]` |
| クエリパラメータ | `[クエリパラメータ パラメータ名]`、省略したときは `[クエリパラメータ パラメータ名 省略]` | `[クエリパラメータ status]`、`[クエリパラメータ page 省略]` |
| 冒頭の表 | `[document.title]`、`[初期フォーカス]`、`[Enter キーで動くボタン]`。場合で違うときは `[初期フォーカス（新規作成）]` | `[document.title（編集）]`、`[初期フォーカス（新規作成）]`、`[Enter キーで動くボタン]` |
| 共通ルールのアクセシビリティ | `[共通ルール アクセシビリティ / 内容]`、部品ごとに作るものは後ろに部品名 | `[共通ルール アクセシビリティ / エラー表示の通知]`、`[共通ルール アクセシビリティ / 確認ダイアログを開いたとき / 削除の確認]` |
| 画面項目の列 | `[項目名 列名]`、エラー表示は画面でまとめて `[エラー表示 表示条件]` | `[「下書き保存」ボタン 表示条件]`、`[「公開する」／「更新する」ボタン 活性条件]`、`[開催日 編集不可条件]`、`[タイトル プレースホルダー]` |
| 表示内容の変換 | `[項目名 表示形式]`（値の読み替えは `[項目名 対応表]` でもよい） | `[ステータス 表示形式]`、`[開催日 表示形式]` |
| 画面項目の備考 | `[項目名 備考の内容]` | `[見出し 文言]`、`[主催者 省略表記]`、`[タグ 対応表]` |
| 遷移 | `[場面]`、条件があれば `[場面 / 条件]`、ブラウザ標準の離脱確認は `[場面 / 離脱確認]`（場面は、遷移を起こすアクション） | `[「← 一覧へ戻る」リンク押下 / 入力内容に変更がないとき]`、`[離脱の確認で「離れる」ボタン押下]`、`[ブラウザの戻る・再読み込み・タブを閉じる / 離脱確認]` |
| 権限 | `[権限 利用者の種類]` | `[権限 member]` |

- 場面は、アクション一覧の「操作」か `初期表示`。1 つのアクションが新規作成と編集で分かれているときは `（新規作成）` `（編集）` を付ける。
- 「操作」に文言が 2 つ並ぶボタン（`「公開する」／「更新する」ボタン押下`）は、API のケースでは「操作」のまま書き、どちらか一方の文言のときだけに当たるケース（そのボタンを押して確かめるバリデーションなど）では、押すほうの文言だけで書いてよい（`「公開する」ボタン押下`）。
- パスは OpenAPI の書き方のまま（`{eventId}` を残す）。
- 1 つのケースが 2 つの出典に当たるときは、` / ` で区切って併記する（`[初期表示 / member のとき / 権限 member]`）。

`test.describe` は次の順に分け、その中を設計書の順に並べる。

1. `API: 初期表示`、`API: 「下書き保存」ボタン押下` のように、API を呼ぶ場面ごと
2. `API を呼ばない手順`
3. `バリデーション・入力できる範囲`
4. `画面項目の条件・値`
5. `遷移`
6. `権限`

API を呼ばない画面では 1 を作らない。該当するケースがない分類は、`describe` ごと作らない。

## 1. API を呼ぶ手順

対象: 「5. 初期表示時の処理」と「6. アクション」で API を呼ぶ手順。

| 設計書の記述 | 作るケース |
| --- | --- |
| リクエストの表 | 手順 1 つにつき 1 ケース。正常な操作をして、表の各行どおりの値（path・query・body）が送られることを確かめる。body は `toEqual` で全体を比べる（送らないはずのプロパティがないことも同時に確かめるため） |
| リクエストの表の「〜なら送らない」「〜のときだけ送る」 | 条件ごとに、送る場合と送らない場合を 1 ケースずつ（上のケースと合わせて満たせばよい） |
| レスポンスの表の各行 | 行ごとに 1 ケース。そのステータスを返し、「処理」の欄の結果（メッセージ、表示の切り替え、遷移、保持した値の使われ方）を確かめる。同じ処理の行（401 など）も、API ごとにケースを作る |
| 項目ごとのエラーの表示先の表（「422 の表示先」） | 表を書いた手順で 2 ケース。エラー表示のある `field` を 1 つ返して `message` が表示されること（422 の行のケースと兼ねてよい）と、`上記以外` に当たる `field` を返して `message` が表示されること（`[… / POST /events 422（上記以外の field）]`）。表を参照しているほかの手順では、422 の行のケースだけを作る |
| レスポンスの表の「上記以外」 | 1 ケース。定義にないステータス（`500`）を返す。通信エラー（`{ networkError: true }`）は、処理が同じなら作らない |
| 「〜して終了する」 | そのケースの中で、後続の手順の API が呼ばれていないことも確かめる（`expect(op.requests).toHaveLength(0)`） |
| 状態の切り替え（「No.35〜37 を非活性にする」→「No.35〜37 の非活性を解除する」、「スピナーを表示する」→「フォームを表示する」など） | 1 ケース。応答を `deferred()` で止め、リクエストが届いたこと（`expect.poll(() => op.requests.length).toBe(1)`）を待ってから途中の状態を確かめ、応答後に戻ることを確かめる。応答後に遷移してしまうステータスでは戻ることを確かめられないので、画面に残るステータス（409 など）を返す |

- 「「5. 初期表示時の処理」の手順 4〜6 と同じ」のように参照している手順は、レスポンスのケースを繰り返さない。リクエストのケースだけ作り、「ただし」で書かれた違い（`page` は 1 など）を確かめる。レスポンスの扱いが違う（表を書き直している）ときは、その表の行ごとにケースを作る。
- 1 つの手順が新規作成と編集で分かれている（「新規作成のとき」「編集のとき」）ときは、それぞれ別の手順として扱う。
- 1 つの手順で複数の API を呼ぶときは、API ごとに上の表のケースを作る。
- 遷移は URL で確かめる（`await expect(page).toHaveURL(...)`）。遷移先の URL は、遷移先の画面の設計書の「URL」から取る。クエリの値（`/login?redirect=` に現在の URL など）も、設計書に書かれていれば確かめる。遷移先の画面の中身は確かめない。

## 2. API を呼ばない手順

対象: 「5. 初期表示時の処理」と「6. アクション」で、API を呼ばない手順（表示の切り替え、ダイアログの開閉、URL パラメータの読み取り、値の保持など）。

| 設計書の記述 | 作るケース |
| --- | --- |
| 手順（「No.38 を表示する」「No.38 を閉じる」など） | 手順ごとに 1 ケース。その手順を起こす操作をして、結果を確かめる |
| 「◯◯なら〜する。なければ〜する。」 | 「なら」と「なければ」で 1 ケースずつ |
| 「◯◯のとき、〜する。」 | 条件を満たす場合と満たさない場合で 1 ケースずつ |
| 「〜して終了する」 | 後続の手順が起きないこと（API が呼ばれない、など）も確かめる |
| URL のクエリパラメータを書き換える手順 | 2 ケース。書き換えたあとの URL のクエリが手順どおりであること（`toHaveURL()`）と、履歴の扱い。`（ブラウザの履歴に追加する）` なら、ブラウザの戻る（`page.goBack()`）で、書き換える前のクエリの同じ画面に戻ること。`（ブラウザの履歴を置き換える）` なら、戻るで、この画面に来る前のページへ移ること（先に別の URL を開いてからこの画面を開いておく） |

- エラー表示を非表示にする手順（「No.7 を非表示にする」「No.23 と No.24 を非表示にする」など）は、先にそのエラー表示にメッセージを出しておき、手順を起こすと消えることで確かめる。エラーを出さずに「表示されていない」を見ても、何も確かめたことにならないため。
- 確認ダイアログの中のボタンのアクションも、ここ（API を呼ぶなら「1.」、遷移するだけなら「5.」）でケースにする。
- 「No.X にフォーカスを移す。」は、その部品にフォーカスがあること（`toBeFocused()`）を確かめる。
- 入力項目を非表示・編集不可にする手順の「入力済みの値は残す」「入力済みの値を消す」は、値を入れてから非表示・編集不可にし、もとに戻したときの値で確かめる。
- 1 つの操作が複数の手順をまとめて起こすとき（「「会場」を選ぶと No.20 を表示し、No.23 と No.24 を非表示にする」）も、手順ごとに別のテストにする。

## 3. バリデーションと入力できる範囲

対象: アクションのチェック表（バリデーション）と、入力項目の表の「入力可能文字種」「入力可能最大文字数」。

### バリデーション

バリデーションは、アクションの見出しが示すタイミングで起こす。

| タイミング | 操作 |
| --- | --- |
| 入力するたび（`No.X に入力`） | `fill()` のあと、何もせずに確かめる |
| フォーカスが外れたとき（`No.X からフォーカスが外れる`） | `fill()` のあと `blur()` してから確かめる |
| 選択を変えたとき（`〜の選択を変更`） | `check()` / `selectOption()` のあとに確かめる |
| 送信時（ボタンのアクションの中） | ほかの項目を正しい値で埋め、ボタンを押してから確かめる。API が呼ばれていないことも確かめる |

違反する値と境目の値は、チェック表の「条件」に書かれた値から作る。

| チェック表の条件 | 作るケース（違反 → メッセージ／境目 → メッセージなし） |
| --- | --- |
| `必須` | 空 → メッセージ |
| `◯ 文字以上` | ◯ − 1 文字 → メッセージ、◯ 文字ちょうど → なし |
| `◯ 文字以内` | ◯ + 1 文字 → メッセージ、◯ 文字ちょうど → なし |
| `使える文字: …` | 並べられていない文字を 1 つ入れる → メッセージ |
| 形式（`https:// で始まる URL 形式` など） | 形式に合わない値 → メッセージ、合う値 → なし |
| 値の範囲（`1〜999`、`今日以降`） | 下限 − 1、上限 + 1 → メッセージ、下限・上限ちょうど → なし |
| `◯ つまで` | ◯ + 1 個目を選ぶ → メッセージ |
| 言葉で書いた条件（「参加者数以上」など） | 条件を破る値 → メッセージ、境目の値 → なし |

- 期待するメッセージは、チェック表の「メッセージ」の ID の文言の変数（`{v1}`、`{v2}`）に、括弧で指定された値を入れたもの。
- チェック表の「表示先」（エラー表示の部品）は、実装の DOM がわからないので、メッセージが画面に表示されていることで確かめる。どの部品の中に出ているかまでは確かめない。
- エラー表示を非表示に戻す手順（「なければ No.10 を非表示にする」「エラーがなかった項目のエラー表示を非表示にする」）があれば、チェック表の「表示先」のエラー表示ごとに 1 ケース作る。エラーを出したあと正しい値に直し、同じタイミングの操作をすると消えることを確かめる（`[タイトル エラーの消去]`）。送信時のバリデーションでは、直したあとの送信に画面に残るステータス（403 など）を返し、その結果を待ってから消えたことを確かめる。
- 同じ項目にチェック表の行が 2 つ以上あるチェック表ごとに、2 つの条件に同時に違反する値を入れ、上の行のメッセージだけが出ることを確かめるケースを 1 つ作る（`[タイトル 優先順位]`）。
- 送信時のバリデーションが別のアクションのバリデーションを参照している（「A2・A4 と同じバリデーションを行う」）ときは、参照先の行を繰り返さない。参照先ごとに 1 ケースだけ、送信時にも同じバリデーションが働くことを確かめる（`[「下書き保存」ボタン押下 / タイトルのバリデーション]`）。
- 「表示していない項目と編集不可の項目はチェックしない」（記述規則で決めた振る舞い）は、該当する項目が画面にあれば、送信時のアクションごとに 1 ケースずつ作る（`[「下書き保存」ボタン押下 / 非表示の項目]`、`[「更新する」ボタン押下 / 編集不可の項目]`）。出典は、実際に押すボタンのアクションにする。
- 「最初のエラー項目までスクロールする」とあれば、押す前に画面の下端までスクロールしておき（`page.mouse.wheel(0, 10000)`）、押したあとにその項目が画面内に入っていることを確かめる（`toBeInViewport()`）。最初から画面内にあると、スクロールしなくても通ってしまうため。422 のレスポンスでスクロールするケースも同じ。
- エラーが出ないこと、API が呼ばれないことを確かめるときは、先に「起きるはずのこと」（エラーの表示など）を待ってから確かめる。
- 境目の値（エラーが出ない側）のケースは、先に違反値でエラーを出しておき、境目の値に直すとエラーが消えることで確かめる。何もせずに「エラーが出ていない」を見ても、バリデーションが走る前に通ってしまうため。送信時のバリデーションなら、API が呼ばれることで確かめる。
- 違反値を入れられないケース（値の範囲の上限 + 1 が、入力可能最大文字数を超えるので入らない、など）は `test.fixme()` にして理由を書く。

### 入力できる範囲

入力項目の表の「入力可能文字種」「入力可能最大文字数」が `-` でない項目ごとに、範囲を超える入力をして、値が範囲に収まることを確かめる。

| 設計書の記述 | 作るケース |
| --- | --- |
| 入力可能最大文字数 | 上限 + 1 文字を 1 文字ずつ入力（`pressSequentially()`）すると、上限の文字数で止まる |
| 入力可能文字種 | 並べられていない文字を入力すると、受け付けない（値に入らない） |
| 備考の変換（全角数字を半角に変換する、など） | 変換元の文字を入力すると、変換後の値になる |
| 貼り付け（備考か、共通ルールに書かれた振る舞い） | 範囲を超える文字列をまとめて入力する（`page.keyboard.insertText()`。クリップボードは使わない）と、書かれたとおり（切り詰める、取り除く）になる |

- アクションに書かれた「入力させない」制限（3 つまでしか選べない、など）は、「2. API を呼ばない手順」のケースとして作る。

### 共通ルール

共通ルール（`common-rules.md`）の「入力」の節のうち、その画面の入力項目に当てはまるものごとに、代表の項目を 1 つ選んで 1 ケース作る。出典は `[共通ルール 項目の名前 / 入力項目の項目名]`（例: `[共通ルール 送信時に前後の空白を取り除くか / タイトル]`）。設定が `TBD` の項目は `test.fixme()` にする。

| 共通ルールの項目 | 作るケース |
| --- | --- |
| 改行を 1 文字と数えるか | 改行を含めて「◯ 文字以内」の ◯ + 1 文字にする。`yes` ならエラーになり、`no` ならエラーにならない |
| 文字数のバリデーション時に前後の空白を取り除くか | 前後に空白を付けて、空白を除くと「◯ 文字以内」の ◯ 文字ちょうどにする。`yes` ならエラーにならず、`no` ならエラーになる |
| 送信時に前後の空白を取り除くか | 前後に空白を付けて保存する。`yes` なら取り除いた値が、`no` なら空白の付いた値が送られる |
| 入力可能文字種・入力可能最大文字数のある項目への貼り付け | 上の「入力できる範囲」の表を見る |

- 共通ルールの「バリデーション」「表示形式」「一覧」「送信」「遷移」の節からは、ケースを作らない。それらは画面設計書にも書かれているので、設計書の記述からケースを作る。
- 共通ルールの「アクセシビリティ」のルールは、設計書の手順には書かれていないので、ここでケースを作る。`common-rules.md` にあるルールだけを対象にする（消されたルールのケースは作らない）。

  | ルール | 作るケース |
  | --- | --- |
  | 入力項目のエラー表示の内容は、その入力項目の説明として伝える | 画面で 1 ケース。入力項目のエラーを 1 つ出し、その入力欄の説明にエラーの文言が入っていること（`toHaveAccessibleDescription()`）を確かめる。どの属性で結び付けているかは見ない |
  | 入力項目に結び付かないエラー表示を表示したときは、読み上げで通知する | 画面で 1 件、`test.fixme()` を置く。通知のしかたは実装によって違い、結果だけでは自動で確かめられないため（理由: 読み上げソフトで手で確かめる） |
  | トーストを表示したときは、読み上げで通知する | 同じく、画面で 1 件の `test.fixme()`（トーストを出す画面だけ） |
  | 送信時にエラーがあるときは、最初のエラー項目にフォーカスを移す | 送信するボタンごとに 1 ケース。エラーのある状態で押し、最初のエラー項目にフォーカスがあること（`toBeFocused()`）を確かめる |
  | 確認ダイアログを開いたときは、フォーカスをダイアログの中の最初のボタンに移す | ダイアログごとに 1 ケース。備考に `初期フォーカス: …` があれば、そのボタン |
  | 確認ダイアログを閉じたときは、開いたボタン・リンクにフォーカスを戻す | ダイアログごとに 1 ケース。やめる側のボタンで閉じて確かめる |
  | 確認ダイアログは Esc キーで閉じられる | ダイアログごとに 1 ケース。Esc キーを押すと閉じ、画面に残ることを確かめる |
  | 一覧を取り直したときは、結果を読み上げで通知する | 同じく、画面で 1 件の `test.fixme()`（一覧のある画面だけ） |
  | Tab キーでフォーカスが移る順序は、部品番号の順にする | 画面で 1 ケース。最初の入力項目から Tab キーを押していき、操作できる部品に部品番号の順でフォーカスが移ることを、最初の 3 つまで確かめる |
  | 文言のない部品には、読み上げ名を付ける | 「4. 画面項目の条件・値」の、備考の読み上げ名のケースで確かめる |

- 日本語入力（IME）の変換中の振る舞い（共通ルール）は、Playwright で再現しにくいので、入力可能文字種・入力可能最大文字数のある項目と、入力するたびにバリデーションをする項目ごとに `test.fixme()` を置いて理由を書く。

## 4. 画面項目の条件・値

対象: 「2. クエリパラメータ」、冒頭の表の「document.title」「初期フォーカス」「Enter キーで動くボタン」と、画面項目の 4 つの表（入力項目、ボタン・リンク、テキスト、その他）の列と備考。

| 設計書の記述 | 作るケース |
| --- | --- |
| クエリパラメータ | パラメータごとに、値を付けて開くケースと、省略して開くケースを 1 つずつ。「用途」に書かれた結果（部品の初期値、API に送る値）を確かめる。初期表示時の処理のリクエストのケースと兼ねてよい。受け取れない値のときの扱いが書かれていれば、そのケースも作る。出典は `[クエリパラメータ パラメータ名]` |
| document.title | 場合ごとに 1 ケース。画面を開いたあとのページのタイトルを確かめる（`toHaveTitle()`） |
| 初期フォーカス（`-` 以外） | 場合ごとに 1 ケース。画面を開いた直後に、書かれた部品にフォーカスがあること（`toBeFocused()`）を確かめる。`-` の場合はケースを作らない |
| Enter キーで動くボタン（`-` 以外） | 2 ケース。1 行の入力欄を 1 つ選び、そこに値を入れて Enter キーを押す（`press('Enter')`）と、そのボタンを押したときと同じ処理が起きること（API を呼ぶボタンなら、同じリクエストが送られること）を確かめる。ボタンに活性条件があれば、非活性のときに Enter キーを押しても何も起きないこと（API が呼ばれないこと）も確かめる。出典は `[Enter キーで動くボタン]`。`-` の場合はケースを作らない |
| 表示条件・活性条件・編集不可条件（`常に表示`、`常に活性`、`-` 以外） | 条件を満たす場合と満たさない場合の 2 ケース。条件が「A のとき、または B のとき」なら、A だけ満たす・B だけ満たす・どちらも満たさないの 3 ケース |
| 初期値 | 新規・編集など初期値の書き分けごとに 1 ケース。画面を開いた直後の値を確かめる。書き分けごとに 1 つのテストで全項目の初期値を確かめてよい（`[入力項目 初期値（新規作成）]`）。表示条件で出し分ける項目（会場名と配信 URL など）は、表示される状態ごとに確かめる（テストデータを変えるか、表示させてから確かめる） |
| プレースホルダー（`-` 以外） | 項目ごとに 1 ケース（`toHaveAttribute('placeholder', ...)`）。配列でまとめる。表示条件のある項目は、表示させてから確かめる（非表示の項目を描画しない実装もあるため） |
| 備考の省略表記（`省略表記: 31 文字以上なら、先頭 30 文字のあとに…を付ける`） | 残す文字数ちょうど → 省略しない、残す文字数 + 1 → 先頭の残す文字数のあとに「…」が付いた文字列になる、の 2 ケース。CSS で省略するもの（行数・幅）は文字列で確かめられないので `test.fixme()` |
| 表示内容に書かれた変換（値の読み替え `draft` は「下書き」、書式 `YYYY/MM/DD`、組み立て、計算、値がないときの表示） | 読み替えは値ごとに 1 ケース（配列でまとめる）。書式・組み立て・計算は 1 ケースずつ。「1 つもないとき」「複数あるとき」のような場合分けは、場合ごとに 1 ケース。モックで返す値は、表示内容に書かれた API のフィールドに入れる |
| 選択肢の対応表（「「会場」は `onsite`」など） | 選択肢ごとに 1 ケース。選んで保存し、その値が送られることを確かめる |
| 文言が条件で変わる | 条件ごとに 1 ケース |
| 処理の手順で表示される部品（確認ダイアログと、その中のボタン） | 開く操作の前に表示されていないケースを、ダイアログごとに 1 つ作る（`[削除の確認 表示条件 / 「キャンセル」ボタン 表示条件 / 「削除する」ボタン 表示条件]`）。開く・閉じるは、アクションのケースで確かめる |
| エラー表示（表示内容が `アクションで指定したメッセージ` の部品） | 画面で 1 ケースだけ。画面を開いた直後に、どのエラー表示のメッセージも表示されていないことをまとめて確かめる（`[エラー表示 表示条件]`）。エラー表示が実装されていなくても通ってしまう弱いケースなので、部品ごとには作らない。表示される側と非表示に戻る側を、バリデーション・API・API を呼ばない手順のケースで、エラー表示ごとに確かめる |
| タグ | ケースは作らない。部品を特定するロケーターを選ぶときに使う（`h1`〜`h3` は `heading`、`button` は `button`、`a` は `link` など） |
| 備考の読み上げ名（`読み上げ名: …`） | 部品ごとに 1 ケース。その名前で部品が見つかること（`getByRole('button', { name: 'メニューを開く' })` が表示されている）を確かめる。`なし（飾り）` はケースを作らない |
| 「表示中は背面の操作をできなくする」 | 1 ケース。表示中に背面の部品を短いタイムアウトで操作しようとすると失敗し（`await expect(locator.click({ timeout: 1000 })).rejects.toThrow()`）、値も変わらないことを確かめる |

- `常に表示`・`常に活性` の部品は、ここではケースを作らない（ほかのケースで操作するため）。
- 権限表や API の振る舞いから実際には起きないとわかる組み合わせ（他の人のイベントは API が 403 を返すので開けない、など）も、条件の組み合わせとして作る。画面が条件どおりに出し分けることを、API の振る舞いに頼らずに確かめるため。モックで作った状態であることをコメントに書く。
- 非活性・編集不可は `toBeDisabled()`、表示・非表示は `toBeVisible()` / `toBeHidden()` で確かめる。

## 5. 遷移

対象: アクションと初期表示時の処理のうち、遷移の手順（「〜へ遷移する」「〜を別タブで開く」）。遷移先・開き方・遷移前の確認は、すべてアクションに書かれている。API の結果で遷移するものは「1. API を呼ぶ手順」のケースで確かめるので、ここでは、API を呼ばずに遷移するアクション（リンクやボタンを押して移るだけのもの）を扱う。

| 設計書の記述 | 作るケース |
| --- | --- |
| 「SCR-NNN 画面名へ遷移する。」 | 押すと、同じタブの URL が遷移先になる |
| 「〜を別タブで開く。」 | 押すと新しいタブが開き、その URL が遷移先になる（`page.waitForEvent('popup')`） |
| 確認ダイアログを経る遷移（「◯◯でないとき、〜へ遷移して終了する。」「No.41 を表示する。」と、ダイアログの中のボタンのアクション） | 条件を満たさないとき確認が出ずに遷移する、条件を満たすとき遷移せずに確認が出る（メッセージの文言も確かめる）、やめるボタンを押すと確認が閉じて画面に残る、進むボタンを押すと遷移する、の 4 ケース。出典は、それぞれのアクション（`[「← 一覧へ戻る」リンク押下 / 入力内容に変更があるとき]`、`[離脱の確認で「離れる」ボタン押下]`） |
| 値の引き渡し（「（`eventId` に `items[].id` を渡す）」） | 遷移先の URL に値が入っていることを、上の遷移のケースの中で確かめる |
| ブラウザ標準の離脱確認 | 条件を満たすとき `beforeunload` のダイアログが出る、満たさないとき出ない、の 2 ケース（`page.close({ runBeforeUnload: true })`）。ブラウザはユーザーが操作していないページでは離脱確認を出さないので、閉じる前に `click()` で実際に操作しておく（`fill()` だけでは操作とみなされない） |

- 遷移先が `TBD` のものは `test.fixme()` にする。

## 6. 権限

対象: 「3. 権限」の表。

- 行ごとに 1 ケース。その利用者として画面を開き（`GET /me` などのモックで利用者を切り替える）、閲覧 `○` なら画面が開くこと、閲覧 `×` なら備考の挙動（遷移、メッセージ）を確かめる。
- 同じ挙動を「1. API を呼ぶ手順」や「2. API を呼ばない手順」のケースで確かめていれば、ここでは作らず、そのケースの出典に併記する（`[初期表示 / member のとき / 権限 member]`）。
- 未ログインの行は、ふつう `GET /me` などの 401 のケースで確かめている。そのケースの出典に `/ 権限 未ログイン` を併記する。

## 作らないケース・作れないケース

- `test.fixme()` にしてよいのは、次の 2 つだけ。「確かめるかどうか決めていない」は理由にならない（設計書に書かれていれば確かめる）。
- `TBD` の欄から作るはずのケースは、`test.fixme()` で名前だけ置く。名前の後ろに `（TBD: 未決事項の内容）` を付ける。
- 設計書の記述どおりに自動で確かめられないケース（CSS で省略するので文字列では確かめられない、目印がないスピナー、IME の変換中、など）も `test.fixme()` にし、理由を名前の後ろに書く。
- 見た目（色・余白・フォント）、設計書に書かれていない文言や振る舞いのケースは作らない。

## 部品の特定（ロケーター）

実装の DOM はわからないので、ワイヤーフレームの文言と、設計書のタグから、役割と文言で特定する。タグが `実装時に決める` の部品（エラー表示、確認ダイアログ、タブ）は、タグを当てにせず、文言や、共通の役割（ダイアログ）で特定する。ファイルの先頭で部品ごとに関数にまとめ、部品番号をコメントに書く。

| 部品 | ロケーター |
| --- | --- |
| 入力欄 | `page.getByLabel(/^タイトル/)`（見出しの「（必須）」などの揺れを吸収するため前方一致）。入力欄を見出しで特定できることが、見出しの部品（`タイトルの見出し`）が表示されていることの確かめにもなるので、入力欄の見出しだけのケースは作らない |
| ラジオ・チェックボックス | `page.getByRole('radio', { name: '会場', exact: true })` |
| ボタン | `page.getByRole('button', { name: '下書き保存', exact: true })` |
| リンク | `page.getByRole('link', { name: '← 一覧へ戻る' })` |
| 見出し | `page.getByRole('heading', { name: 'イベントを編集' })`（レベルでは特定しない。共通のヘッダーも見出しのことがあるため） |
| ダイアログ | `page.getByRole('dialog').or(page.getByRole('alertdialog'))`（どちらの役割で作られていても見つかるようにする） |
| メッセージ・テキスト | `page.getByText(M.MSG018)` |

- 前方一致の正規表現が別の部品にも当たらないか確かめる（`/^会場/` は「会場名」にも当たる）。
- 文言が同じ部品が複数あるときは、親の領域で絞る（`dialog.getByRole('button', { name: '削除する' })`）。
- 確認ダイアログが複数ある画面でも、同時に表示されるのは 1 つという前提で、上のロケーターで特定してよい。
- 実装の文言がワイヤーフレームと違ったときは、テスト側ではなく設計書・ワイヤーフレームを直すかをユーザーに確認する。

## メッセージ

メッセージ一覧（`messages.md`）のうち、この画面の設計書が参照しているメッセージを、テストファイルの先頭で `M` 定数にする。キーは ID からハイフンを除いたもの（`MSG-018` → `MSG018`）。テスト名には ID ではなく文言を入れる（`q(M.MSG018)`）。

- 変数（`{v1}`、`{v2}`…）のある文言は、関数にする。引数は変数の番号の順（`MSG004: (v1: string, v2: number) => ...`）。呼ぶときは、設計書の参照で指定された値を渡す（`MSG-004（v1: タイトル、v2: 50）` → `M.MSG004('タイトル', 50)`）。API の値が指定されている変数（`` `participantCount` ``）には、テストデータの値を渡す。
- `<br>` で複数行になる文言は、行の配列にし、行ごとに確かめる（`MSG017: (title: string) => ['…', '…']`）。

## モック

- 各テストで、画面を開く前に必要な API をすべて `api.on()` で登録する。画面を開く手順は `openNew()`、`openEdit()` のような関数にまとめ、正常系の応答を登録してから `page.goto()` する。
- 異常系は、テストの中で同じ操作を `api.on()` し直して上書きする（後から登録したものが優先される）。
- 別の画面へ遷移するケースでは、遷移させる操作の直前に `api.allowUnmockedCalls()` を呼ぶ。遷移先の画面が呼ぶ API はモックしていないので、そのままだと「モックしていない API が呼ばれた」として失敗するため。遷移しないケースや、遷移する前にこの画面の通信を確かめたいケースでは、確かめ終わるまで呼ばない。
- 遷移したあとでこの画面を開き直す（201 のあと編集として開き直す、など）ときは、開き直したときに呼ぶ API もモックする。
- レスポンスの body は OpenAPI のスキーマに合わせて書く。テストデータはファイルの先頭にまとめ、`{ ...draftEvent, status: 'published' }` のように上書きして使う。
- 422 の body は OpenAPI のエラーの形で作り、その中の文言が画面に出ることを確かめる。

## モーダルだけの画面

独立した画面 ID を持つモーダルは、親画面を開いてモーダルを開く操作までを、画面を開く関数（`openDialog()` など）にまとめる。親画面の API もモックする。テストで確かめるのはモーダルの設計書の内容だけにする。
