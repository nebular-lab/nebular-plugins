# 整合性チェックのプロンプト

画面設計書（`.md`）とワイヤーフレーム（`.html`）を書いたり直したりしたあとに、サブエージェントへ渡して食い違いを探させるためのプロンプト。書いた本人は自分の思い込みに引きずられて見落としやすいので、別のエージェントに読ませる。

## 使い方

1. 下の「プロンプト」の `{...}` を埋める。
2. Agent ツールで汎用のサブエージェントを起動し、埋めたプロンプトを渡す。完了を待つ。
3. 返ってきた「エラー」を直す。直したら、エラーがなくなるまで 1〜3 を繰り返す。「警告」は内容を見て、直すか、ユーザーに伝えるかを決める。

番号の食い違いのうち、ワイヤーフレームの番号自体がおかしいもの（重複・順序など）は、設計書の側で合わせ込まない。番号の正はワイヤーフレームにあるため。

## プロンプト

````text
あなたは画面設計書のレビュアーです。次のファイルを読み、下の観点で食い違いを探してください。ファイルは編集しないでください。

- 対象の画面: {画面 ID。複数なら列挙}
- 画面設計書とワイヤーフレームの置き場所: {例: docs/screens/}
- OpenAPI 定義: {パス。なければ「なし」}
- 記述規則: {write-screen-spec/references/writing-rules.md の絶対パス}
- ワイヤーフレームの規則: {write-screen-wireframe/references/wireframe-rules.md の絶対パス}

記述規則とワイヤーフレームの規則は、最初に全部読んでください。以下の観点は、それらの規則に照らして確かめるものです。

## 1. ワイヤーフレーム単体
- `data-no` の値は、先頭が 0 でない半角数字の整数だけか（`7-1` のような枝番、全角数字、空の値はエラー）。
- 1 つの `.screen` の中で同じ番号を 2 回使っていないか。
- 最初の `.screen`（`data-title` が「通常」で始まるもの）で、番号が上から順（DOM の順）に並んでいるか。
- 2 つ目以降の `.screen` で、最初の `.screen` にすでにある番号を振り直していないか（その状態で初めて出る部品にだけ番号を付ける規則）。
- 全 `.screen` を通して、番号が 1 から欠けずに続いているか（欠けていれば警告）。
- `input`、`select`、`textarea`、`.modal`、`.error` に `data-no` を付けていないか（付けるのは包んでいる `label` や `.dialog`）。
- `style` 属性、`<style>`、`<script>`、規則にないクラスを使っていないか。

## 2. ワイヤーフレームと設計書の番号
- ワイヤーフレームの番号が、設計書の「画面項目」の 4 つの表（入力項目、ボタン、リンク・画面遷移、テキスト・その他）のどれか 1 つに、ちょうど 1 回ずつ載っているか。
- 画面項目の表にあって、ワイヤーフレームにない番号はないか。
- 設計書の本文で参照している番号（`No.12`、`No.16〜18` のような範囲、`No.6、No.7` のような列挙、アクション一覧の「対象」列、入力チェック表の No 列、備考や処理の中の `No.X`）が、すべてワイヤーフレームに存在するか。範囲は展開して確かめる。
- 番号と部品の中身が合っているか（例: 設計書で No.6 を「タイトル」の入力欄としているのに、ワイヤーフレームの No.6 が別の部品になっていないか）。番号がずれたまま残っている疑いがあれば、どの番号がどの番号にずれているかを推測して書く。
- 同じ画面 ID の設計書やワイヤーフレームが 2 つ以上ないか。

## 3. 設計書の中の対応
- 節の構成が記述規則どおりか（1 概要、2 権限、3 画面項目、4 初期表示時の処理、5 アクション、6 メッセージ、7 未決事項）。
- アクション一覧の ID と、`### A1.` のような詳細の節の ID・順序が一致しているか。一覧にないアクションや、節のないアクションはないか。
- ボタンの「押したときの処理」に書いたアクション ID が存在するか。
- メッセージの表の ID が、本文のどこかから参照されているか。本文で使っているのに表にない ID はないか。
- 「「4. 初期表示時の処理」の手順 4〜6 と同じ」や「A5 の手順 4 と同じ」のような参照が、実在して意図に合う手順を指しているか。
- 入力チェック表の「条件」が、入力項目の表の列名（必須、最小文字数、最大文字数、最大選択数、使用できる文字種）か、備考に書いた制約（形式、範囲など）に対応しているか。入力項目の表で `-` の列を条件に使っていないか。
- 空欄のセルが残っていないか（`-` か `TBD` のはず）。`TBD` があるのに未決事項に対応する行がないものはないか。
- 上限や文字種のある入力項目（最大文字数・使用できる文字種・最大選択数・範囲のどれかが `-` でない項目）で、「入力制限」の列が決まっているか（空欄でないか）。
- 「入力制限」に並べた制約が、入力項目の表や備考に実在するか。入力制限に並べた制約を、チェック表にも書いていないか（入力させない制約はチェックしない規則）。逆に、入力制限に並べていない上限・文字種の制約が、どこかのチェック表にあるか（なければ、違反してもエラーが出ないことになる）。
- 画面一覧（`README.md`）に「入力の共通ルール」の節があるか。

## 4. OpenAPI との対応（OpenAPI 定義がある場合）
- 設計書に書いたメソッドとパス、operationId が OpenAPI に存在するか。
- リクエストの表の「場所」と「パラメータ」が、OpenAPI の `in` と名前に合っているか。OpenAPI で必須のパラメータ・プロパティが抜けていないか。
- レスポンスの表に、OpenAPI でその操作に定義されたステータスがすべてあり、最後に「上記以外」の行があるか。定義にないステータスを書いていないか。
- 設計書で参照しているレスポンスのフィールド（`items[].title` など）が、OpenAPI のスキーマに存在するか。

## 報告の形
次の形で、日本語で報告してください。問題がなかった観点は「問題なし」と 1 行書いてください。

```
## エラー
- [ファイル:行] 何が食い違っているか。どう直せばよいか。
## 警告
- [ファイル:行] ...
## 問題なし
- 1. ワイヤーフレーム単体
- ...
```

「エラー」は規則に反していて直す必要があるもの、「警告」は規則違反とは言い切れないが確認したほうがよいものです。
````
