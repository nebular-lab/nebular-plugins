# 整合性チェックのプロンプト

画面設計書（`.md`）とワイヤーフレーム（`.html`）を書いたり直したりしたあとに、サブエージェントへ渡して食い違いを探させるためのプロンプト。書いた本人は自分の思い込みに引きずられて見落としやすいので、別のエージェントに読ませる。

## 使い方

1. 下の「プロンプト」の `{...}` を埋める。
2. Agent ツールで汎用のサブエージェントを起動し、埋めたプロンプトを渡す。完了を待つ。
3. 返ってきた「エラー」を直す。直したら、もう一度 1〜3 を行う。チェックは最大 3 回までにし、3 回目でも残ったエラーは直さずに、報告でユーザーに伝える（指摘が出続けて終わらなくなるのを防ぐため）。「警告」は内容を見て、直すか、ユーザーに伝えるかを決める。

番号の食い違いのうち、ワイヤーフレームの番号自体がおかしいもの（重複・順序など）は、設計書の側で合わせ込まない。番号の正はワイヤーフレームにあるため。

## プロンプト

````text
あなたは画面設計書のレビュアーです。次のファイルを読み、下の観点で食い違いを探してください。ファイルは編集しないでください。

- 対象の画面: {画面 ID。複数なら列挙}
- 画面設計書とワイヤーフレームの置き場所: {例: docs/screens/}（共有ファイルの `overview.md`、`messages.md`、`common-rules.md` もここにある）
- OpenAPI 定義: {パス。なければ「なし」}
- 記述規則: {write-screen-spec/references/writing-rules.md の絶対パス}
- ワイヤーフレームの規則: {write-screen-wireframe/references/wireframe-rules.md の絶対パス}

記述規則とワイヤーフレームの規則は、最初に全部読んでください。以下の観点は、それらの規則に照らして確かめるものです。

## 1. ワイヤーフレーム単体
- `data-no` の値は、先頭が 0 でない半角数字の整数だけか（`7-1` のような枝番、全角数字、空の値はエラー）。
- 1 つの `.screen` の中で同じ番号を 2 回使っていないか。
- 最初の `.screen`（`data-title` が「通常」で始まるもの）で、番号が上から順（DOM の順）に並んでいるか。
- 2 つ目以降の `.screen` で、最初の `.screen` にすでにある番号を振り直していないか（その状態で初めて出る部品にだけ番号を付ける規則）。
- 2 つ目以降の `.screen` で初めて出る部品の番号が、規則の「状態」のとおりか（通常の部品と並んで出る部品は位置に合わせて割り込ませ、通常の部品に置き換わって出る部品とモーダルは最後の番号の続き）。
- 全 `.screen` を通して、番号が 1 から欠けずに続いているか（欠けていれば警告）。
- `input`、`select`、`textarea`、`.modal` に `data-no` を付けていないか（付けるのは包んでいる `label` や `.dialog`）。
- エラー表示（`.error`）に `data-no` が付いているか。最初の `.screen` に描かれているか（その入力欄が 2 つ目以降の `.screen` で初めて出る場合と、通常の部品に置き換わって出るエラー表示の場合は、その `.screen` に描かれていればよい）。
- バリデーションのある入力欄の下と、画面上部に、エラー表示が描かれているか（なければ警告）。
- 画面の中に出す確認ダイアログが、`.modal` と `.dialog` で描かれ、`.dialog` とその中のボタンに番号が付いているか。
- `style` 属性、`<style>`、`<script>`、規則にないクラスを使っていないか。

## 2. ワイヤーフレームと設計書の番号
- ワイヤーフレームの番号が、設計書の「画面項目」の 3 つの表（入力項目、ボタン・リンク、テキスト・その他）のどれか 1 つに、ちょうど 1 回ずつ載っているか。
- 画面項目の表にあって、ワイヤーフレームにない番号はないか。
- 設計書の本文で参照している番号（`No.12`、`No.16〜18` のような範囲、`No.6、No.7` のような列挙、アクション一覧の「対象」列、バリデーションのチェック表の No 列、備考や処理の中の `No.X`）が、すべてワイヤーフレームに存在するか。範囲は展開して確かめる。
- 番号と部品の中身が合っているか（例: 設計書で No.7 を「タイトル」の入力欄としているのに、ワイヤーフレームの No.7 が別の部品になっていないか）。番号がずれたまま残っている疑いがあれば、どの番号がどの番号にずれているかを推測して書く。
- 同じ画面 ID の設計書やワイヤーフレームが 2 つ以上ないか。

## 3. 設計書の中の対応
- 節の構成が記述規則どおりか（1 概要、2 クエリパラメータ、3 権限、4 画面項目、5 初期表示時の処理、6 アクション、7 未決事項）。メッセージの節を画面ごとに持っていないか。
- アクション一覧の ID と、`### A1.` のような詳細の節の ID・順序が一致しているか。一覧にないアクションや、節のないアクションはないか。
- アクション ID が `A1` から欠番なく続き、対象の部品番号の順（部品のない操作は最後）に並んでいるか。
- 本文で参照しているアクション ID と手順番号（「A6 の手順 8 と同じ」、表示条件の「A8 で表示し、A9、A10 で閉じる」など）が実在し、意図に合う手順を指しているか。アクションを足したあとに番号がずれたまま残っている疑いがあれば、どうずれているかを推測して書く。
- 設計書で使っているメッセージ ID（`MSG-001` の形）が、すべて `messages.md` にあるか。
- 変数（`{v1}`、`{v2}`…）のあるメッセージを参照している箇所すべてで、括弧に、そのメッセージのすべての変数の値が指定されているか（`MSG-004（v1: タイトル、v2: 50）`。バリデーションのチェック表でも省略しない）。変数の数が `messages.md` の文言と合っているか。変数のないメッセージに括弧を付けていないか。チェック表では、項目名の値がその行の「項目」と合い、数値がその行の「条件」の値と合っているか（「50 文字以内」なのに `v2: 100` になっていないか）。
- `messages.md` の変数が `{v1}` からの連番で、`{項目名}` のような名前の変数が残っていないか。「表示場所」の列が残っていないか。
- `messages.md` に、文言が同じ、または項目名や数値だけが違うメッセージが重複していないか（変数でまとめられるもの）。ID が重複していないか（使わなくなった ID の欠番はあってよい）。
- 対象の画面が置き場所のすべての画面であるときだけ: `messages.md` に、どの設計書からも参照されていないメッセージがないか。
- `overview.md` の「画面一覧」に対象の画面の行があり、画面名・URL が設計書と合っているか。ワイヤーフレーム・設計書・E2E テストの列のリンク先が実在するか（ないものは `-`）。冒頭のファイルの表に、画面ごとのファイル（ワイヤーフレーム、設計書、E2E テスト）の行を書いていないか。
- 「「5. 初期表示時の処理」の手順 4〜6 と同じ」や「A5 の手順 4 と同じ」のような参照が、実在して意図に合う手順を指しているか。
- バリデーションのチェック表の「条件」が、記述規則の書き方（必須、◯ 文字以上、◯ 文字以内、使える文字: …、形式、値の範囲、◯ つまで）に沿い、値が書かれているか。
- 空欄のセルが残っていないか（`-` か `TBD` のはず）。`TBD` があるのに未決事項に対応する行がないものはないか。
- 冒頭の表に「Enter キーで動くボタン」の行があり、ボタンが 1 つ、番号と文言で書かれているか（`-` と `TBD` を除く）。その番号が、ワイヤーフレームと「ボタン・リンク」の表にあるボタンか。アクション一覧の「操作」や見出しに、Enter キーのことを重ねて書いていないか。
- 冒頭の表に「初期フォーカス」の行があり、書かれた部品番号がワイヤーフレームにあるか（`-` と `TBD` を除く）。
- 入力項目を非表示・編集不可にする手順に、入力済みの値を残すか消すかが書かれているか。
- 選択肢を API から取る・条件で変える記述が、入力項目の備考ではなく、初期表示時の処理かアクションに書かれているか。
- ワイヤーフレームのエラー表示（`.error`）が、設計書の「テキスト・その他」の表に、項目名 `◯◯のエラー`、タグ `実装時に決める`、表示内容 `アクションで指定したメッセージ` で載っているか。エラーの文を、表示内容にメッセージ ID で直接書いた部品がないか。
- エラー表示の「表示条件」が、切り替えるアクション（と「5. 初期表示時の処理」）の並びだけで書かれ、条件そのものが書かれていないか。並べたアクションのそれぞれに、そのエラー表示を表示するか非表示にする手順が実際にあるか（ほかの手順を参照して行う場合を含む）。逆に、そのエラー表示を切り替える手順があるのに、表示条件に並んでいないアクションはないか。
- エラー表示を表示する手順ごとに、非表示に戻す手順がどこかにあるか（ないと、エラーが出たままになる）。入力項目を非表示にする手順で、その項目のエラー表示も非表示にしているか。
- 確認ダイアログ（ワイヤーフレームの `.dialog`）が、表示内容にメッセージ ID、表示条件に開く・閉じるアクションを書いているか。ダイアログの中のボタンが「ボタン・リンク」の表にあり、それぞれにアクションがあるか。アクションの手順に「MSG-NNN の確認を表示する」のように、部品にしていない確認が残っていないか（ブラウザ標準の確認を除く）。
- API が項目ごとのエラーを返すステータス（422 など）の処理に、フィールドと表示先の対応表（最後に `上記以外` の行）があるか、または対応表への参照があるか。対応表の `field` が OpenAPI のプロパティ名と合い、表示先の番号がエラー表示の部品か。
- バリデーションのチェック表に「表示先」の列があり、エラー表示の部品番号が書かれているか。バリデーションでエラーを出す入力項目に、エラー表示の部品があるか。
- メッセージを表示する手順のすべてに、どこに出すかが書かれているか。エラー表示の部品に出すなら表示先の部品番号（「MSG-022 を No.6 に表示する」）、部品に出さないなら出し方（「MSG-013 をトーストで表示する」）。「MSG-013 を表示する」のように、どこに出すかがわからない手順が残っていないか。
- 各表の備考に、操作や処理によって起きること（処理中の非活性、二重送信の防止、待機表示、切り替えで取り直す、など）が書かれていないか。備考の内容が、記述規則の「備考に書くこと」の範囲か。
- 処理中の非活性を解除する手順が「非活性を解除する」と書かれているか（「活性に戻す」「活性にする」は不可）。非活性にする手順ごとに、解除する手順があるか。
- ワイヤーフレームのラベルに「（必須）」とある入力項目に、チェック表の条件 `必須` の行があるか。逆に、`必須` の行がある項目のラベルに「（必須）」がないものはないか（どちらも警告）。
- 手順にぶら下げた表や段落の字下げが、手順の番号の幅（手順 1〜9 は 3 文字、手順 10 以降は 4 文字）になっているか。
- 画面項目の 3 つの表に「タグ」の列があり、ワイヤーフレームのその番号の要素のタグ名と合っているか（入力項目は `label` の中の入力欄で、`input` は `type` も合っているか）。エラー表示・確認ダイアログ・タブは `実装時に決める` になっているか（`-` や空欄は不可）。「種類」の列が残っていないか。タグの列や備考に、`role` や `aria-*` などの属性を書いていないか。
- 冒頭の表に「タイトル」の行があるか。
- 「2. クエリパラメータ」の節に、表（パラメータ、値、省略したとき、用途）か「なし」が書かれているか。初期表示時の処理やアクションで `` URL クエリ `xxx` `` と書いたパラメータが、すべてこの表にあるか。表にあるのに、どの手順でも使われていないパラメータはないか。
- URL のクエリパラメータを書き換える手順のすべてに、`（ブラウザの履歴に追加する）` か `（ブラウザの履歴を置き換える）` が書かれているか。ルーターの関数名など、特定のライブラリの名前を書いていないか。
- 文言のない部品（ワイヤーフレームの `.image`、`.icon` だけのボタンやリンク）の備考に `読み上げ名: ` があるか。
- 共通ルールのアクセシビリティで決まっていること（エラー時や確認ダイアログでのフォーカスの移動、Esc キー、読み上げでの通知）を、アクションの手順に重ねて書いていないか。
- 「省略表記」の列が残っていないか（省略表記は、備考に `省略表記: ` で始めて書く）。
- 画面項目の表に、アクションに書くべきことが書かれていないか。入力項目の表に必須・文字数のチェック・エラーの列や記述がないか。ボタン・リンクの表に、押したときの処理・遷移先・開き方・遷移前の確認が書かれていないか。
- 入力可能文字種・入力可能最大文字数で入力できないようにしたものを、バリデーションのチェック表にも書いていないか（入力可能最大文字数が 3 の項目に「3 文字以内」の行があるなど）。
- ボタン・リンクの表の部品のうち、押したときに何かが起きるものすべてに、対応するアクション（アクション一覧の「対象」にその No がある）があるか。遷移の手順が、記述規則の「遷移」の形（「〜へ遷移する」「〜を別タブで開く」）で書かれているか。
- 置き場所に `common-rules.md`（共通ルール）があるか。
- 設計書が共通ルールの設定と食い違っていないか（バリデーションのタイミングが、react-hook-form の `mode` と `reValidateMode` の設定と合うか、送信中のボタンの非活性、未保存の変更があるときの離脱確認、数値のカンマ、一覧の検索条件の復元）。食い違いは警告として挙げる（その画面・その項目だけ違う扱いにしていることがある）。設定が `TBD` の項目は対象外。
- `common-rules.md` の項目・選択肢が、共通ルールの項目の一覧（write-screen-common-rules/references/viewpoints.md）のとおりで、「設定」が選択肢のどれか 1 つか `TBD` になっているか。

## 4. OpenAPI との対応（OpenAPI 定義がある場合）
- 設計書に書いたメソッドとパス、operationId が OpenAPI に存在するか。
- リクエストの表の「場所」と「パラメータ」が、OpenAPI の `in` と名前に合っているか。OpenAPI で必須のパラメータ・プロパティが抜けていないか。
- レスポンスの表に、OpenAPI でその操作に定義されたステータスがすべてあり、最後に「上記以外」の行があるか。定義にないステータスを書いていないか。
- 設計書で参照しているレスポンスのフィールド（`items[].title` など）が、OpenAPI のスキーマに存在するか。

## 報告の形
次の形で、日本語で報告してください。問題がなかった観点は「問題なし」と 1 行書いてください。

```
## エラー
- [ファイル:行] 何が食い違っているか。どう直せばよいか。
## 警告
- [ファイル:行] ...
## 問題なし
- 1. ワイヤーフレーム単体
- ...
```

「エラー」は規則に反していて直す必要があるもの、「警告」は規則違反とは言い切れないが確認したほうがよいものです。
````
