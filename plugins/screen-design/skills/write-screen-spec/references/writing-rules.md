# 画面設計書の記述規則

設計書を誰が書いても同じ形になるように、何をどこに書くかを決める。ここに書くのは考え方と決まりだけ。表の列、言い回し、具体的な書き方は [サンプル](../../../examples/docs/screens/) の設計書（`SCR-NNN_*/SCR-NNN_*.md`）に合わせる。規則にもサンプルにもない判断をしたときは、ユーザーに伝える。

## 基本の考え方

- 設計書だけを読めば、画面に何があり、どう動くかがわかるようにする。ワイヤーフレームや API 定義を見ればわかることでも、設計書に書く。
- 同じことを 2 か所に書かない。片方だけ直されて食い違うため。どこに書くかは下の決まりに従う。
- 「どう見えるか」は画面項目の表に、「操作したら何が起きるか」はアクションに、「開いたときに何が起きるか」は初期表示時の処理に書く。アクションや初期表示時の処理に書けることは、表の備考に書かない。
- 画面どうしは独立させる。ほかの画面と同じ処理があっても、「◯◯画面と同じ」と書かず、その画面の設計書に全部書く。
- 文体は常体。画面上の文言は「」、API のパスやフィールド名は `` ` `` で囲む。該当しない欄は `-`、決まっていない欄は `TBD` と書き、空欄を残さない。
- 特定のライブラリの名前や、実現のしかた（属性など）は書かない。利用者に何が起きるかを書く。

## 構成

ファイルは、保存先の画面ごとのフォルダの中の `SCR-NNN_<slug>/SCR-NNN_<slug>.md`。同じフォルダに、その画面のワイヤーフレーム（`.html`）と Playwright テスト（`.spec.ts`）を置く。画面 ID は一度振ったら変えず、再利用しない。節は次の順で、名前と順序を変えない。該当するものがない節や表は、見出しを残して「なし」と書く。

1. 概要
2. クエリパラメータ
3. 閲覧権限
4. 画面項目（入力項目 / ボタン・リンク / テキスト / その他）
5. 初期表示時の処理
6. アクション
7. 未決事項

冒頭の表には、画面 ID、画面名、URL、`document.title`、共通ヘッダー、初期フォーカス、Enter キーで動くボタン、ワイヤーフレームへのリンク、更新日を書く。

- 初期フォーカス、Enter キーで動くボタンは、部品を番号と名前で書く。なければ `-`。
- Enter キーで動くボタンは、ボタンだけを書く。1 行の入力欄にフォーカスがあるときに Enter キーを押すと、そのボタンのアクションが動く（ボタンが非活性なら何も起きない）。アクションの側には Enter キーのことを書かない。

## 共通ヘッダー

複数の画面で同じヘッダーを使うときは、ヘッダーを画面の設計書に書かず、共通ヘッダーとして 1 回だけ書く。

- 種類が違うヘッダー（ログイン後の画面のもの、ログインしていなくても見られる画面のもの、など）は、別の共通ヘッダーに分ける。1 つの設計書の中で、場合分けしない。
- 共通ヘッダーには `HDR-NNN` の ID を振り、画面と同じように、フォルダ `HDR-NNN_<slug>/` の中に、ワイヤーフレームと設計書を作る。ID は一度振ったら変えず、再利用しない。
- 設計書の節は、概要、変数、画面項目、初期表示時の処理、アクション、未決事項（[header-template.md](../assets/header-template.md)）。書き方は、画面の設計書と同じ。URL、クエリパラメータ、閲覧権限は書かない。
- 画面によって変わる内容（画面名など）は、変数 `{v1}`、`{v2}` にする。ヘッダーの設計書の「変数」に、それぞれ何を入れる変数かを書く。
- 画面の設計書の冒頭の表の「共通ヘッダー」に、どのヘッダーを使うかを、ヘッダーの設計書へのリンクで書き、変数に入れる値をすべて指定する（`HDR-001 ログイン後のヘッダー（v1: イベント一覧）`）。ヘッダーを使わない画面は `-`。
- 画面の設計書には、ヘッダーの中の部品もアクションも書かない。番号も振らない。画面の手順からヘッダーに触れるときは、「共通ヘッダー」と書く。
- ヘッダーが表示する API の値を、ヘッダーが自分で取るのか、ヘッダーを置く画面が取ったものを使うのかを、ヘッダーの設計書の「初期表示時の処理」に書く。

## クエリパラメータ

URL の `?` 以降で受け取るパラメータを、すべて表に書く。受け取る値、省略したときの扱い、用途に加えて、受け取れない値が来たときの扱いも決める。手順の中で使うパラメータは、すべてこの表にある状態にする。

## 閲覧権限

利用者の種類ごとに、この画面を閲覧できるかどうかだけを、`○` か `×` で書く。備考の列はない。

- 閲覧できない利用者が開いたときの動き（別の画面へ移す、メッセージを出す）は、ここではなく「5. 初期表示時の処理」の手順に書く。
- 利用者の種類によって部品の表示や活性が変わるなら、その部品の表示条件・活性条件に書く。
- 利用者の種類によって処理が変わるなら、そのアクションの手順に書く。

## 画面項目

ワイヤーフレームで番号を振った部品を、すべて、次の 4 つの表のどれか 1 つに書く。番号はワイヤーフレームのものをそのまま使う。

| 表 | 入れる部品 |
| --- | --- |
| 入力項目 | 値を入力・選択する部品 |
| ボタン・リンク | 押す部品 |
| テキスト | 文や値を表示するだけの部品（見出し、文、表のセル、項目名） |
| その他 | 上のどれでもない部品（領域、表、画像、タブ、エラー表示、確認ダイアログなど） |

- **タグ**: 部品の種類は、HTML の要素のタグ名で表す（種類の列はない）。入力項目は `input` の `type` まで書く。設計の時点で決めないものは「実装時に決める」と書く。エラー表示、確認ダイアログ、タブのように、使うライブラリで要素が変わるものがこれに当たる。属性（`role` など）は書かない。
- **項目名とデータ**: 項目名（見出し・ラベル）とデータは、別の部品にする。フォームの見出しと入力欄、表の見出しのセルとデータのセルも同じ。
- **入力項目**: 入力可能文字種と入力可能最大文字数は、入力欄そのものが受け付ける範囲（それ以外は打っても入らない）。入力はできるがエラーにしたいもの（必須、文字数、形式など）は、ここではなくアクションのバリデーションに書く。必須かどうかの列はない。
- **活性条件**: 入力項目も、ボタン・リンクも、操作できる条件を「活性条件」に書く（同じ向きにそろえる。「編集不可条件」のように、できない条件では書かない）。条件を満たさないときは非活性で、フォーカスも当たらない。常に操作できるなら「常に活性」と書く。
- **ボタン・リンク**: 表示条件と活性条件だけを書く。押したときの処理や遷移先は書かない。
- **API の値**: どの API のどのフィールドかがわかるように書く（`` `GET /events/{eventId}` の `title` ``）。フィールド名だけを書かない。条件や備考に書くときも同じ。
- **値の変換**: 取った値を変換して表示するとき（読み替え、書式、組み立て、計算、値がないときの表示）は、備考ではなく表示内容に書く。
- **エラー表示**: 画面の中に出すエラーは、出す場所を部品にする。いつ表示し、いつ非表示に戻すかは、すべて手順に書く。表示条件の欄には、切り替えるアクションを並べるだけにする。
- **まとまりと中身**: まとまり（ヘッダー、確認ダイアログ、タブ、選択肢のまとまりなど）と、その中の文言や部品は、別の行に書く。まとまりの行の表示内容に、中の文言をまとめて書かない。
- **確認ダイアログ**: 画面の中に出す確認は、ダイアログと、中の見出し・文・ボタンを部品にし、中のボタンにもアクションを立てる。ブラウザ標準の確認は部品にせず、手順に文章で書く。
- **読み上げ名**: 文言のない部品（アイコン、画像、アイコンだけのボタンやリンク）と、文言だけでは区別できない部品（一覧の行ごとにある、同じ文言のボタンやリンク）には、スクリーンリーダーに読み上げさせる名前を、備考に書く。飾りで、読み上げる必要のないものは、そう書く。文言がそのまま名前になる部品には書かない。
- **備考**: 列のない情報だけを書く（省略表記、読み上げ名、固定の選択肢と値の対応、並び順など）。操作や処理で起きることは書かない。

## 共有するファイル

画面をまたぐものは、設計書に書かず、保存先の共有ファイルに 1 回だけ書く。

| ファイル | 内容 |
| --- | --- |
| `overview.md` | 冒頭に、全画面で共有するファイルの表。続けて、共通ヘッダーの一覧と、画面一覧（使う共通ヘッダーと、ワイヤーフレーム・設計書・Playwright テストへのリンク）。`README.md` や `screens.md` は作らない |
| `messages.md` | 全画面で共通のメッセージ。列は ID・種別・文言 |
| `storage.md` | ブラウザに保存する値（ブラウザのストレージを使う画面があるときだけ作る） |
| `common-rules.md` | 全画面で同じになる扱い（`/write-screen-common-rules` で決める） |
| `screen-flow.drawio` | 画面遷移図（`/write-screen-flow` で作る） |
| `wireframe.css`、`api-mock.ts` | ワイヤーフレームの共通スタイルと、Playwright テストで API をモックする補助 |

**メッセージ**

- 設計書からは ID で参照する。文言の中で値が変わる箇所は `{v1}`、`{v2}` と書き、使う側で、すべての変数に入れる値を指定する（`MSG-004（v1: タイトル、v2: 50）`）。
- 項目名や数値だけが違う文言は、変数を使って 1 つにまとめる。足す前に、同じ意味のものがないかを探す。
- どこに出すかは、メッセージ一覧ではなく使う側に書く。エラー表示に出すなら表示先の部品番号を、部品に出さないなら出し方（トーストなど）を、必ず書く。

**ブラウザストレージ**

画面がブラウザに値を保存するとき（localStorage、sessionStorage、Cookie、IndexedDB など）は、何をどこにどんな形で置くかを `storage.md` に書く。データベースの設計書に当たるもの。使う画面がなければ作らない。作ったら、`overview.md` の冒頭の表に行を足す。

- 1 つのキーを 1 行にし、`STG-NNN` の ID を振る。ID は一度振ったら変えず、再利用しない。足す前に、同じ用途のものがないかを探す。
- 保存先、キー、内容、値の形式、保存期間（何もしなければいつまで残るか）を書く。値が構造を持つなら、フィールドの表を「値の構造」に書く。
- キーの中で値が変わる箇所は `{v1}`、`{v2}` と書き、使う側で、すべての変数に入れる値を指定する（`STG-002（v1: eventId の値）`）。
- いつ保存し、いつ読み、いつ消すかは、ストレージ一覧ではなく、使う画面の手順に ID で書く。読む手順には、値がないときと、値が形式に合わないときの扱いも書く。
- 画面のスクリプトから読み書きしないもの（サーバーが設定して、ブラウザが自動で送るだけの Cookie）は書かない。
- 値の形式を変えるときは、前の形式の値が利用者のブラウザに残っている。そのときの扱いを決めて、読む手順に書く。

**共通ルール**

設計書は、共通ルールを既定として書く。設計書に書く欄があることは、設計書にも共通ルールのとおりに書く（「共通ルールのとおり」と略さない）。欄がないこと（入力の扱い、応答を待つ時間の上限、トーストの重なり、ブラウザの戻るでの復元、アクセシビリティ、ライブラリの設定）は書かない。その画面だけ違う扱いにするときは、設計書に書く。

## 処理の書き方

「5. 初期表示時の処理」と「6. アクション」は、起きる順に、番号付きの手順で書く。

- 1 手順に 1 つの処理。分岐は「◯◯のとき、〜する。」と書き、途中で終わるなら「〜して終了する。」と書く。
- 状態による表示の切り替え（読み込み中、エラー、処理中の非活性など）は、その状態になる手順と、元に戻す手順の両方を書く。
- 入力項目を非表示・非活性にする手順には、入力済みの値を残すか消すかを書く。
- 部品は番号で書く。

**アクション**

- 最初に、アクションの一覧（ID、操作、対象）を置き、そのあとにアクションごとの手順を書く。
- ボタンとリンクは、押したときに何かが起きるものすべてにアクションを立てる。部品のない操作（ブラウザの戻るなど）も、動きがあるなら立てる。
- 並び順は対象の部品番号の順（部品のない操作は最後）で、ID はその順に `A1` から欠番なく振る。増減したら振り直す。

**遷移と URL**

- 別の画面へ移る処理は、遷移先を画面 ID と画面名で書く。別タブで開くなら、そう書く。
- 遷移は履歴に追加するのが既定。URL のクエリパラメータを書き換える手順には、「ブラウザの履歴に追加する」か「ブラウザの履歴を置き換える」かを必ず書く。

**バリデーション**

- すべてアクションに書く。いつチェックするかは設計者が決め、実際にチェックするタイミングごとにアクションを立てる（既定は共通ルール）。
- チェックの内容は、表（No、項目、条件、メッセージ、表示先）で書く。条件には値まで書き、1 行に 1 つの条件にする。上の行を優先する。
- 表示していない項目と、非活性の項目はチェックしない。入力可能文字種・入力可能最大文字数で入力できないものは、チェックに書かない。

**API の呼び出し**

- API は OpenAPI で定義されている前提で、パス・パラメータ・ステータスを定義と一致させる。
- 呼ぶ手順は、手順の文、リクエストの表（各パラメータに入れる値の出どころ）、レスポンスの表（ステータスごとの処理）の 3 つを 1 組で書く。
- レスポンスの表には、定義されているステータスをすべて書き、最後に「上記以外」を置く。
- API が項目ごとのエラーを返すときは、どのフィールドのエラーをどのエラー表示に出すかの対応表を書く（最後に「上記以外」）。
- 同じ画面の中で同じ API を同じ扱いで呼ぶ手順は、2 回目以降、最初の手順を参照して違うところだけを書いてよい。

## 決まっていないこと

- 決まっていない欄は `TBD` と書き、「7. 未決事項」に質問の形で残す。もっともらしい値を勝手に入れない。
- ワイヤーフレームや OpenAPI と、会話の内容が食い違ったら、会話の内容を採用し、食い違いを未決事項に残す。
