# 画面設計書の記述規則

設計書を誰が書いても同じ形になるように、表記と書き方をそろえる。迷ったらこの規則と [サンプル](../../../examples/docs/screens/) に従い、規則にない判断をしたときはユーザーに伝える。

## 目次

- ファイルと ID
- 番号
- 表記
- 冒頭の表
- クエリパラメータ
- 権限
- 画面項目（入力項目 / ボタン・リンク / テキスト / その他 / API の値と変換 / 項目名とデータ / エラー表示 / 確認ダイアログ / 備考に書くこと）
- 共有するファイル（概要と画面一覧 / メッセージ一覧 / 共通ルール）
- 処理の書き方（アクション一覧 / 遷移）
- バリデーション
- API の呼び出し
- 決まっていないこと

## ファイルと ID

- ファイル名は `SCR-NNN_<slug>.md`。`NNN` は 3 桁ゼロ埋めの連番、`<slug>` は英小文字とハイフン（例: `SCR-003_order-detail.md`）。
- 画面 ID は一度振ったら変えない。画面を廃止しても ID は再利用しない。
- ダイアログやモーダルも、独立した操作があるなら 1 画面として ID を振る。ワイヤーフレームの描き方は wireframe-rules.md の「モーダルだけの画面」に従う。単なる確認ダイアログ（「削除しますか？」程度）は親画面の部品として描き、親画面のアクションに書く（「確認ダイアログ」を見る）。

## 番号

- 部品の番号（No）は、ワイヤーフレームの `data-no` をそのまま使う。画面項目・アクションで共通。設計書の側で付け直さない。
- 振り方の規則（通し番号、順序、モーダルの扱いなど）は [wireframe-rules.md](../../write-screen-wireframe/references/wireframe-rules.md) の「部品番号」に従う。
- アクションは `A1`、`A2`…と、画面内で欠番のない連番にする。並び順は「アクション一覧」で決める。アクションを足したり消したりしたら振り直し、設計書の中の参照（`A6 の手順 8`、表示条件の `A8 で表示し…` など）も直す。
- メッセージは画面ごとに振らず、全画面で共通のメッセージ一覧（`messages.md`）の ID（`MSG-001`）を使う。

## 表記

- 文体は常体で、体言止めか「〜する」で短く書く。「です・ます」は使わない（例: 「一覧画面へ遷移する」）。
- 画面上の文言は「」で囲み、ワイヤーフレームの表記どおりに書く（例: 「保存」ボタン）。
- 他の画面は `SCR-NNN 画面名` で書く。
- API のパス・パラメータ名・レスポンスのフィールド名は `` ` `` で囲む（例: `GET /events`、`eventId`、`items[].title`）。
- 表のセルに複数の内容を書くときは `<br>` で区切る。
- 該当しない欄は `-`、決まっていない欄は `TBD`。空欄は残さない（空欄だと「該当なし」か「書き忘れ」か区別できないため）。
- 該当する部品がない表（入力項目のない画面の「入力項目」など）は、見出しを残し、表を置かずに「なし」とだけ書く。節の中身がない場合も同じ。

## 冒頭の表

| 行 | 書き方 |
| --- | --- |
| 画面 ID・画面名 | `overview.md` の画面一覧と同じ |
| URL | 複数あるとき（新規作成と編集など）は `<br>` で並べ、括弧で場合を書く |
| document.title | ブラウザのタブに出る、ページのタイトル。画面を開いたときに最初に読み上げられる。場合で違うときは `<br>` で並べる（`イベントを作成<br>イベントを編集`） |
| 初期フォーカス | 画面を開いたときにフォーカスを置く部品を、`No.9 タイトル` のように番号と項目名で書く。場合で違うときは `新規作成: No.9 タイトル<br>編集: -` のように並べる。どこにも置かないなら `-`。決まっていなければ `TBD` |
| Enter キーで動くボタン | 入力欄で Enter キーを押したときに動くボタン（送信ボタン）を、`No.9 「検索」` のように番号と文言で 1 つ書く。場合で違うときは `新規作成: No.36 「公開する」<br>編集: -` のように並べる。Enter キーを押しても何も起きない画面は `-`。決まっていなければ `TBD` |
| ワイヤーフレーム | 設計書から見た相対パスのリンク |
| 更新日 | 設計書を書いた・直した日 |

API 定義（OpenAPI）とメッセージ一覧（`messages.md`）へのリンクは、冒頭の表には書かない。どちらも全画面で共通のファイルで、置き場所は `overview.md` と各 skill の手順でわかるため。

「Enter キーで動くボタン」に書いたボタンは、ブラウザの標準のフォームの動きに合わせて、次のように動く。どの入力欄で押したときかは、設計書には書かない。

- 画面の中の 1 行の入力欄（テキスト入力、数値入力、日付入力など）のどれかにフォーカスがあるときに Enter キーを押すと、そのボタンのアクションが動く。
- そのボタンが非活性、または非表示のときは、何も起きない。
- 複数行の入力欄（テキストエリア）では改行になる。日本語入力の変換を確定するための Enter キーでは動かない。
- どこにもフォーカスがないときは、何も起きない。ボタンにフォーカスがあるときは、そのボタン自身が押される。
- アクション一覧の「操作」には Enter キーのことを書かない（「「検索」ボタン押下」とだけ書く）。同じことを 2 か所に書かないため。

初期フォーカス以外のフォーカスの移動（エラーが出たときに最初のエラー項目へ移す、など）は、ここではなくアクションの手順に書く（「処理の書き方」を見る）。

## クエリパラメータ

「1. 概要」の次に `## 2. クエリパラメータ` の節を置き、その画面が URL の `?` 以降で受け取るパラメータを、すべて表に書く。受け取らない画面は、表を置かずに「なし」と書く。

| 列 | 書き方 |
| --- | --- |
| パラメータ | パラメータの名前を `` ` `` で囲んで書く（`keyword`） |
| 値 | 受け取る値。決まった値のどれかなら並べ（`` `published`、`draft`、`closed` ``）、そうでなければ形を書く（`文字列`、`1 以上の整数`、`YYYY-MM-DD`） |
| 省略したとき | パラメータがないときにどう扱うか（`空`、`1`、`「すべて」のタブを選ぶ`）。なければ画面を開けないなら `必須` |
| 用途 | 何に使うか（どの部品の初期値になるか、どの API のどのパラメータに使うか）。受け取れない値が来たときの扱いが、省略したときと違うなら、それも書く |

- URL のパスに入る値（`/events/{eventId}/edit` の `eventId`）は、ここではなく冒頭の表の「URL」に書く。
- この画面が自分で書き換えるパラメータ（検索条件、ページなど）も、ここに書く。書き換える処理は、アクションの手順に書く（「処理の書き方」の「URL の書き換えと履歴」）。
- 初期表示時の処理やアクションで `` URL クエリ `xxx` `` と書いたパラメータは、すべてこの表にある状態にする。

## 権限

- 「閲覧」は `○`（閲覧できる）か `×`（閲覧できない）のどちらか。
- 閲覧できない利用者がアクセスしたときの挙動（ログイン画面へ遷移する、など）は備考に書く。

## 画面項目

部品を次の 4 つに分け、それぞれの表に書く。1 つの部品は 1 つの表にだけ書く。ワイヤーフレームで番号を振った部品は、すべてどれかの表に書く。各表の中は No の昇順に並べる。

| 分類 | 対象 |
| --- | --- |
| 入力項目 | テキスト入力、テキストエリア、数値入力、日付入力、パスワード入力、セレクト、ラジオ、チェックボックス、トグル |
| ボタン・リンク | ボタン、リンク |
| テキスト | 文や値を表示するだけの部品。見出し、文、表のセル、項目名（見出し・ラベル）など。タグが `h1`〜`h3`、`p`、`span`、`small`、`label`、`th`、`td`、`li` のもの |
| その他 | 上の 3 つのどれでもない部品。領域（ヘッダー、フッターなど）、表、一覧、画像、アイコン、タブ、エラー表示、確認ダイアログ、読み込み中の表示など |

「テキスト」と「その他」を 1 つの表にまとめない。該当する部品がない表は、見出しを残して「なし」と書く。

画面項目の表には、部品が「どう見えるか」（何が入力でき、いつ表示され、いつ押せるか）だけを書く。「操作したら何が起きるか」（バリデーション、押したときの処理、遷移、選択肢の切り替え、値のクリア、フォーカスの移動）は表に書かず、すべて「6. アクション」に書く。画面を開いたときに決まることは「5. 初期表示時の処理」に書く。アクションや初期表示時の処理に書けることは、表の備考ではなくそちらに書く。同じことを 2 か所に書くと、片方だけ直されて食い違うため。

### 入力項目

| 列 | 書き方 |
| --- | --- |
| タグ | 下の「タグ」を見る。入力欄の種類は、タグで表す（`input（type="text"）`、`textarea`、`select`、`input（type="radio"）` など） |
| 入力可能文字種 | 入力欄が受け付ける文字種を、受け付けるものだけで並べる（`<br>` 区切り）。ここに書いていない文字は入力できない（打っても入らない）。「◯◯以外」「◯◯を除く」のような禁止の書き方はしない。どの文字も入力できるなら `-`。例: `半角数字`、`半角英数字<br>半角記号` |
| 入力可能最大文字数 | 入力欄が受け付ける文字数の上限。数字だけ書く（例: `3`）。これを超えては入力できない。上限なく入力できるなら `-`。セレクトなど文字を入力しない項目は `-` |
| 初期値 | 画面を開いたときの値。API の値を入れるなら、どの API かを付けて `` `GET /events/{eventId}` の `title` `` のように書く（下の「API の値と変換」を見る） |
| プレースホルダー | 表示する文言を「」で書く。なしは `-` |
| 編集不可条件 | 入力できなくなる条件（例: `status` が `published` のとき）。常に編集できるなら `-` |

「入力可能文字種」と「入力可能最大文字数」は、入力欄そのものが受け付ける範囲であり、エラーを出すチェックではない。

- 入力はできるが、エラーにしたいもの（必須、最小文字数、最大文字数、使える文字、形式、値の範囲など）は、この表に書かず、アクションのバリデーションに書く。
- 同じ項目で両方を決めてよい（例: 入力可能最大文字数は `-` で何文字でも入力でき、バリデーションで「50 文字以内」をエラーにする。または、入力可能最大文字数を `3` にして 4 文字目を入力させない）。
- 変換して受け付けるもの（全角数字を半角に変換する、など）は、備考に書く。
- 貼り付けや日本語入力（IME）の変換中の扱いは、共通ルール（`common-rules.md`）に従う。その項目だけ違うときは備考に書く。
- 文字数や文字種以外の「入力させない」制限（チェックボックスを 3 つまでしか選べない、過去の日付を選べない、など）は、その操作のアクションに書く。
- 必須かどうかの列はない。項目が必須かどうかは、アクションのチェック表に条件 `必須` の行があるかどうかで決まる。見出しの「（必須）」は、画面に表示するだけのテキストである。見出しの部品（`タイトルの見出し`）の表示内容に「タイトル（必須）」と書き、入力項目の項目名には含めない。

### ボタン・リンク

| 列 | 書き方 |
| --- | --- |
| タグ | 下の「タグ」を見る。ボタンは `button`、リンクは `a` |
| 表示条件 | 画面に表示される条件。常に表示なら `常に表示`。条件を満たさないときに別の見せ方をするなら、それも書く（例: 「それ以外はリンクにせず文字だけ表示する」） |
| 活性条件 | 押せる条件。条件を満たさないときは非活性（グレーアウト）で表示する。常に押せるなら `常に活性` |

- 押したときの処理、遷移先、開き方（同一タブ／別タブ）、遷移前の確認は、この表に書かない。アクションに書く。
- ボタンもリンクも、押したときに何かが起きるものは、必ずアクションを 1 つ立てる（「アクション一覧」を見る）。

### テキストとその他の列

「テキスト」の表と「その他」の表は、同じ列を使う。

| 列 | 書き方 |
| --- | --- |
| タグ | 下の「タグ」を見る。エラー表示、確認ダイアログ、タブは `実装時に決める` |
| 表示内容 | 見出し・ラベル・案内（「条件に合うイベントはありません」など）のような画面の固定文言は「」で直接書く。確認ダイアログの文は、メッセージ ID（`MSG-017`）で書く。エラーの文はここに書かず、エラー表示の部品にする（下の「エラー表示」を見る）。API の値と、その値の変換の書き方は、下の「API の値と変換」を見る |
| 表示条件 | 表示される条件（例: ログイン中のユーザーの `role` が `admin` のとき）。常に表示なら `常に表示` |

### API の値と変換

画面項目の表に API から取った値を書くときは、どの API のレスポンスの、どのフィールドかがわかるように書く。表示内容と初期値だけでなく、表示条件・活性条件・編集不可条件・備考に書くときも同じ（`` `GET /events/{eventId}` の `status` が `draft` のとき ``）。

- `` `メソッド パス` の `フィールド` `` の形で書く（`` `GET /events/{eventId}` の `organizerName` ``、`` `GET /events` の `items[].title` ``）。`` `organizerName` `` のように、フィールド名だけを書かない。同じ表のほかの行で API を書いていても、行ごとに省かずに書く。1 行だけを読んでも、どこから来た値かがわかるようにするため。
- 1 つの部品に、同じ API の値を 2 つ使うときは、API を 1 回書いて並べてよい（`` `GET /events/{eventId}` の `participantCount` と `capacity` ``）。
- メッセージの変数に API の値を入れるときも同じ（`MSG-017（v1: `GET /events/{eventId}` の `title`）`）。
- API の値ではないもの（URL クエリ、入力値、固定の文言）は、それぞれ `` URL クエリ `keyword` ``、`No.9 の入力値`、「」で書く。

取った値をそのまま表示せず、変換して表示するときは、変換のしかたを備考ではなく表示内容に書く。値の出どころと、どう見えるかを、1 つの欄で読めるようにするため。値の出どころを 1 行目に書き、変換を `<br>` で区切って続ける。

| 変換 | 書き方の例 |
| --- | --- |
| 値の読み替え | `` `GET /events/{eventId}` の `status`<br>`draft` は「下書き」、`published` は「公開中」、`closed` は「終了」と表示する `` |
| 書式 | `` `GET /events/{eventId}` の `startDate`<br>`YYYY/MM/DD` で表示する `` |
| 複数の値の組み立て | `` `GET /events/{eventId}` の `participantCount` と `capacity`<br>「{participantCount} / {capacity} 人」で表示する `` |
| 計算 | `総ページ数は `GET /events` の `total` ÷ `perPage` の切り上げ` |
| 別の API の値への引き当て | `` `GET /categories` の `items[]` のうち、`id` が `GET /events/{eventId}` の `categoryId` と同じものの `name` `` |
| 値がないとき・複数あるとき | `複数あるときは「、」で区切る。1 つもないときは「なし」と表示する` |

- 長いときに「…」で省略する省略表記だけは、これまでどおり備考に書く（「備考に書くこと」を見る）。
- 入力項目の、選択肢と値の対応（「会場」は `onsite`）や、入力中の変換（全角数字を半角に変換する）は、表示の変換ではないので、備考に書く。

### 項目名とデータ

項目名（見出しやラベル）とデータを並べて表示するところ（「カテゴリ」と「勉強会」、「主催」と「山田 花子」など）は、項目名とデータを別の部品にして、それぞれ 1 行ずつ書く。「主催: {organizerName}」のように、1 つの部品の表示内容や備考にまとめない。

| 部品 | 項目名の列 | 表示内容 |
| --- | --- | --- |
| 項目名のほう | `カテゴリの見出し`、`主催者の見出し` のように、`◯◯の見出し` | 固定の文言を「」で書く（「カテゴリ」） |
| データのほう | `カテゴリ`、`主催者` | API の値（`` `GET /events/{eventId}` の `organizerName` ``） |

- 項目名のほうの表示条件は、データと同じなら `No.6 と同じ` と書く。
- フォームの入力欄も同じ。見出し（ラベル）と入力欄を別の部品にする。見出しは「テキスト」の表に `タイトルの見出し`（タグは `label`。ラジオやチェックボックスをまとめた項目の見出しは `span`）、表示内容は「タイトル（必須）」のように書き、入力欄は「入力項目」の表に `タイトル` と書く。入力欄に表示条件があるときは、見出しの表示条件を `No.20 と同じ` と書く。見出しを持たないチェックボックス 1 つ（文言がそのまま選択肢のもの）は、入力項目の 1 行だけでよい。
- 表の見出しのセルは、1 つずつ部品にする。繰り返す表（一覧）の列の見出しも同じで、列ごとに `タイトルの見出し`、`ステータスの見出し` のように 1 行ずつ書く。表の部品の備考にまとめて書かない。表示条件は、表と同じなら `No.11 と同じ` と書く。

### エラー表示

画面の中に出すエラーメッセージ（入力項目の下に出すもの、画面上部に出すもの、一覧の代わりに出すものなど）は、出す場所を 1 つの部品として「その他」の表に書く。ワイヤーフレームにも描き、番号を振る。出すメッセージが 1 つに決まっている場合も、表示内容にメッセージ ID を直接書かず、この形にそろえる。

| 列 | 書き方 |
| --- | --- |
| 項目名 | `タイトルのエラー`、`画面上部のエラー` のように、どこのエラーかがわかる名前 |
| タグ | `実装時に決める` |
| 表示内容 | `アクションで指定したメッセージ`。どのメッセージを出すかは、アクションのチェック表や手順で決まる |
| 表示条件 | 表示・非表示を切り替えるアクションを並べる（例: `A2、A6、A7 で切り替える`。初期表示時の処理で切り替えるなら `「5. 初期表示時の処理」` も並べる）。条件そのものは書かない |

- エラー表示は、画面を開いた時点ではどれも非表示にする。
- いつ表示し、いつ非表示に戻すかは、すべて初期表示時の処理とアクションの手順に書く（「MSG-022 を No.7 に表示する」「No.7 を非表示にする」）。表示条件の欄に条件を書くと、手順と食い違うため。非表示に戻す手順を書き忘れると、エラーが出たままになるので、表示する手順ごとに、どこで非表示に戻るかを確かめる。
- バリデーションでエラーを出す入力項目には、エラー表示の部品を 1 つずつ用意する。
- 入力項目を非表示にする手順では、その項目のエラー表示も非表示にする。
- トーストのように、一時的に重ねて出して自動で消えるメッセージは部品にしない。アクションの手順に「MSG-013 をトーストで表示する」と書くだけにする。

### 確認ダイアログ

画面の中に出す確認ダイアログ（「削除しますか？」「入力内容が保存されていません」など）は、すべて部品にする。ワイヤーフレームに描き、ダイアログと、その中のボタンに番号を振る。

| 部品 | 書く表 | 書き方 |
| --- | --- | --- |
| ダイアログ | その他 | 項目名は `削除の確認` のように、何の確認かがわかる名前。タグは `実装時に決める`。表示内容はメッセージ ID（`MSG-017（v1: `title`）`）。表示条件は、開くアクションと閉じるアクション（`A8 で表示し、A9、A10 で閉じる`） |
| ダイアログの中のボタン | ボタン・リンク | 表示条件は `No.38 を表示しているとき` |

- ダイアログを開く手順は「No.38 を表示する。」、閉じる手順は「No.38 を閉じる。」と書く。
- ダイアログの中のボタンにも、1 つずつアクションを立てる（`削除の確認で「キャンセル」ボタン押下`）。確認のあとの処理（API を呼ぶ、遷移する）は、進むボタンのアクションに書く。
- ブラウザ標準の確認（ページを離れるときの離脱確認など）は、文言もボタンも指定できないので部品にしない。アクションの手順に文章で書く。

### タグ

部品の種類（テキスト入力、ボタン、見出しなど）を書く列はない。4 つの表のどれにも「タグ」の列を置き、その部品を実装するときの HTML の要素を `` ` `` で囲んで書く。ワイヤーフレームを見ればわかることでも、設計書に書く。設計書だけを読んで、見出しの階層や入力欄の種類がわかるようにするため。

- ワイヤーフレームで `data-no` を付けた要素のタグ名を、そのまま書く（`h1`、`p`、`a`、`button`、`table`、`header`）。ワイヤーフレームと違うタグを書かない。変えたいときは、ワイヤーフレームを `/write-screen-wireframe` で直す。
- 入力項目は、番号を付けた `div` ではなく、中の入力欄を書く。見出しのほうは `label`（まとめた項目の見出しは `span`）と書く。`input` は `type` も書く（`input（type="text"）`、`input（type="date"）`、`input（type="checkbox"）`）。そのほかは `textarea`、`select`。
- 見出しは、階層がわかるように `h1`〜`h3` を書く。
- 書くのは HTML の要素のタグ名だけ。`role` や `aria-*` などの属性は書かない。どの属性で実現するかは、使うコンポーネントライブラリによって変わるため。
- タグを設計の時点で決めず、実装するときに決める部品は、`実装時に決める` と書く（`-` や空欄にしない）。HTML の要素そのものに意味がない部品（エラー表示、確認ダイアログ・モーダル、タブ）は、使うコンポーネントライブラリによって要素が変わるので、これに当たる。何の部品かは項目名でわかるようにし（`タイトルのエラー`、`削除の確認`、`ステータスのタブ`）、どう振る舞うかは共通ルールのアクセシビリティで決まる。ワイヤーフレームでは `p`、`small`、`div` で描いているが、それは図のための要素なので、設計書には写さない。
- それ以外の部品でも、要素を設計の時点で決めきれないものは `実装時に決める` と書いてよい。
- 文や値を出すだけの部品（`p`、`span`、`td`）は、ワイヤーフレームのタグ名をそのまま書く。
- 画像は `img` と書き、備考に読み上げ名を書く（下の「読み上げ名」）。

### 備考に書くこと

列を用意していない情報は、各表の「備考」に書く。備考に書くのは次の内容に限る。これ以外の情報が必要になったら、列を足すか、この一覧に追加することをユーザーに相談する。書くことがなければ `-`。

| 表 | 備考に書く内容 |
| --- | --- |
| 入力項目 | 固定の選択肢と、その値の対応（「会場」は `onsite` など）。選択肢を API から取るときや、条件で選択肢が変わるときは、ここではなく初期表示時の処理かアクションに書く<br>表示条件（常に表示でない場合）<br>変換して受け付けるもの（全角数字を半角に変換する、など）<br>貼り付け・IME の扱いが共通ルールと違う場合 |
| ボタン・リンク | 文言が条件で変わるとき、その条件と文言<br>省略表記（下を見る）<br>読み上げ名（下を見る） |
| テキスト | 省略表記（下を見る） |
| その他 | 並び順<br>1 ページあたりの件数<br>読み上げ名（下を見る）<br>表示する位置（ワイヤーフレームだけではわからない場合）<br>確認ダイアログを開いたときにフォーカスを置くボタン（最初のボタン以外に置く場合だけ。`初期フォーカス: No.43`）<br>確認ダイアログの表示中に背面を操作できるか<br>省略表記（確認ダイアログの中の値を省略するとき） |

**読み上げ名**

文言のない部品（画像、アイコンだけのボタン）と、文言だけでは区別できない部品（一覧の各行にある「編集」リンクなど）には、備考に `読み上げ名: ` で始めて、読み上げさせる名前を書く。どの属性で実現するかは、設計書には書かない。

- 例: `読み上げ名: メニューを開く`、`読み上げ名: {title} を編集`（API の値を入れるときは `{ }` で書く）
- 飾りの画像（意味を持たないもの）は `読み上げ名: なし（飾り）` と書く。
- 文言がそのまま名前になる部品（文言のあるボタン、ラベルのある入力欄）には書かない。

**省略表記**

長い文言を「…」で省略するときは、備考に `省略表記: ` で始めて書く（列は用意していない）。省略しない部品には書かない。

- 文字数で省略するなら、残す文字数と「…」の付け方を書く（例: `省略表記: 31 文字以上なら、先頭 30 文字のあとに…を付ける`）。
- 行数や幅で省略するなら、CSS で省略することを書く（例: `省略表記: 2 行を超えたら CSS で末尾を…にする`）。
- 表示内容の一部だけを省略するなら、どの値かを書く（例: `省略表記: `title` が 21 文字以上なら、先頭 20 文字のあとに…を付ける`）。

備考には、操作や処理によって起きること（処理中に非活性にする、待機表示を出す、タブを切り替えると取り直す、など）を書かない。それらはアクションと初期表示時の処理にだけ書く。備考に書くのは、操作しても変わらない性質だけにする。

## 共有するファイル

画面をまたいで使うものは、画面ごとの設計書に書かず、保存先（既定は `docs/screens/`）の共有ファイルに 1 回だけ書く。同じことを画面ごとに書くと、片方だけ直されて食い違うため。雛形は [write-screen-wireframe/assets/shared/](../../write-screen-wireframe/assets/shared/) にある。

| ファイル | 内容 |
| --- | --- |
| `overview.md` | 概要。ファイルの説明と、画面一覧 |
| `messages.md` | メッセージ一覧 |
| `common-rules.md` | 共通ルール |
| `screen-flow.drawio` | 画面遷移図（`/write-screen-flow` で作る。描き方はその skill の規則に従う） |

### 概要と画面一覧（overview.md）

`overview.md` には、冒頭にファイルの説明の表を、続けて「画面一覧」の節を置く。`README.md` と `screens.md` は作らない。

**ファイルの説明**

- 見出しは立てず、タイトルのすぐ下に、説明の文を 1 つと表を置く。列は「ファイル、内容」。
- 全画面で共有するファイルだけを、1 行ずつ並べる（メッセージ一覧、共通ルール、画面遷移図、ワイヤーフレームの共通スタイル）。実際にあるファイルだけを書く。画面遷移図の行は、`/write-screen-flow` が作ったときに足す。API 定義（OpenAPI）がこの保存先の外にあるときも、ここに 1 行で書く（`overview.md` から見た相対パスのリンク）。
- 画面ごとに作るもの（ワイヤーフレーム、画面設計書、Playwright テスト）は、ここには書かず、下の画面一覧に書く。

**画面一覧**

- 画面 ID の順に 1 画面 1 行。列は「画面 ID、画面名、URL、ワイヤーフレーム、設計書、Playwright テスト」。
- ワイヤーフレーム・設計書・Playwright テストの列には、その画面のファイルへのリンクを書く（`overview.md` から見た相対パス）。まだないものは `-` にする。
- URL が複数ある画面（新規作成と編集など）は `<br>` で並べる。
- 画面を廃止しても行は消さず、画面名の後ろに `（廃止）` と書く（ID を再利用しないため）。

### メッセージ一覧（messages.md）

画面に出すメッセージ（エラー・確認・完了・お知らせ）は、全画面で共通の 1 つの表に書き、設計書からは ID で参照する。

| 列 | 書き方 |
| --- | --- |
| ID | `MSG-001` からの連番（3 桁ゼロ埋め）。種別を問わず、追加した順に振る。一度振った ID は変えず、使わなくなっても再利用しない。複数人が同時にメッセージを足すと同じ ID が重なることがあるので、足す直前に最新の `messages.md` を読み、マージで重なったら後から足した側を振り直す |
| 種別 | `エラー`、`確認`、`完了`、`お知らせ` |
| 文言 | 画面に出す文言をそのまま。値が入る箇所は、変数 `{v1}`、`{v2}`…で書く（出てくる順に番号を振る）。複数行は `<br>` で区切る。確認ダイアログのボタンの文言は書かない（ボタンは画面の部品として設計書に書く） |

どこに表示するか（項目のエラー表示、画面上部、トーストなど）は、メッセージ一覧には書かない。メッセージを使う側（各画面の設計書）で決める。

**変数**

- 文言の中で値が変わる箇所は、`{v1}`、`{v2}` のように、文言に出てくる順に番号を振った変数で書く（`{v1}は {v2} 文字以内で入力してください`）。`{項目名}` のような名前は付けない。
- 同じ値を 2 回使うときは、同じ変数を 2 回書く。
- 変数に何を入れるかは、メッセージ一覧には書かない。メッセージを使う側で指定する（下の「設計書からの参照」）。

**文言をまとめる**

- 項目名や数値だけが違う文言は、変数を使って 1 つのメッセージにまとめる（`{v1}を入力してください`、`{v1}は {v2} 文字以内で入力してください`）。言い回しを全画面でそろえるため。
- 新しいメッセージを足す前に、同じ意味のメッセージがすでにないかを `messages.md` で探す。あればそれを使う。言い回しだけが違う場合は、既存のものに合わせる。
- その画面にしかない文言（「イベントを公開しました」など）は、変数にせずそのまま書く。
- すでに使われているメッセージの文言を変えると、それを参照するすべての画面に影響する。変数の数や順番を変えるときも同じ。変える前に、どの画面で使われているかを調べてユーザーに確認する。

**設計書からの参照**

- ID で参照する（`MSG-022 を No.7 に表示する`）。
- 変数のあるメッセージは、ID の後ろに括弧で、すべての変数に入れる値を指定する（`MSG-004（v1: タイトル、v2: 50）`、`MSG-009（v1: 定員、v2: 1、v3: 999）`）。省略はしない。バリデーションのチェック表でも、項目名を入れる変数を含めて、すべて書く。
- 値は、固定の文字や数（`タイトル`、`50`）か、API の値（`` `participantCount` ``、`` `title` ``）で書く。
- どこに、いつ出るかは、メッセージを参照している箇所でわかるようにする。
  - バリデーションのエラー: アクションのチェック表に、条件と ID と表示先を書く
  - 処理の中で、画面の中のエラー表示に出すもの: 初期表示時の処理・アクションの手順やレスポンスの表に、表示先の部品番号を付けて書く（「MSG-022 を No.7 に表示する」）
  - 処理の中で、トーストで出すもの: 「MSG-013 をトーストで表示する」と書く。部品に出さないメッセージは、出し方（トーストなど）を必ず書く。メッセージ一覧に表示場所がないので、書かないとどこに出るかがわからないため
  - 確認ダイアログ: 「その他」の表の、確認ダイアログの部品の「表示内容」に ID を書く。いつ出るかは、そのダイアログを表示するアクションの手順でわかる
- バリデーションのエラーは、1 つの条件に 1 つのメッセージを使う（必須・文字数・使える文字は別のメッセージ）。条件ごとに文言を変えられるようにするため。
- どの画面からも参照されていないメッセージは置かない（ID は欠番にする）。

### 共通ルール（common-rules.md）

どの画面でも同じになる扱いを、決まった項目ごとに、選択肢から選んで書いたもの。項目と選択肢は [viewpoints.md](../../write-screen-common-rules/references/viewpoints.md) で決めており、`/write-screen-common-rules` で作る。

| 節 | 項目 |
| --- | --- |
| 入力 | 改行を 1 文字と数えるか、文字数のバリデーション時に前後の空白を取り除くか、送信時に前後の空白を取り除くか、入力可能文字種・入力可能最大文字数のある項目への貼り付け、日本語入力（IME）の変換を確定する前の文字にも、入力の制限とバリデーションを行うか |
| 表示形式 | 数値を 3 桁ごとにカンマで区切るか |
| 一覧 | 再読み込みやブラウザの戻るで一覧に戻ったときに、検索条件とページを復元するか |
| 送信 | 送信中にボタンを非活性にするか |
| 遷移 | 未保存の変更があるときに離脱確認をするか |
| アクセシビリティ | 選択肢のない、決まったルール（読み上げでの通知、エラー時や確認ダイアログでのフォーカスの移動、Esc キー、Tab キーの順序、読み上げ名） |
| react-hook-form のデフォルト設定 | `mode`、`reValidateMode` |
| TanStack Query の設定（defaultOptions） | queries の `staleTime`、`gcTime`、`refetchOnMount`、`refetchOnWindowFocus`、`refetchOnReconnect`、`retry`、mutations の `retry` |

画面設計書は、共通ルールを既定として書く。

- 設計書に書く欄があること（バリデーションのタイミング、ボタンの非活性、離脱確認、数値の表示形式、一覧の検索条件の復元）は、設計書にも共通ルールのとおりに書く。「共通ルールのとおり」と略さない。設計書だけを読んでも動きがわかるようにするため。
- 設計書に書く欄がないこと（「入力」の節の項目、TanStack Query の設定）は、設計書には書かない。
- アクセシビリティのルールは、設計書の手順には書かない（「エラー項目にフォーカスを移す」「ダイアログを開いたらフォーカスを移す」などを、アクションに 1 つずつ書かない）。どの画面にもそのまま適用される。設計書に書くのは、備考の `読み上げ名: …` と、確認ダイアログの `初期フォーカス: …` だけ。
- その画面・その項目だけ共通ルールと違う扱いにするときは、欄があればその欄に書き（バリデーションのタイミングなら、そのタイミングのアクションを立てる）、なければ備考に `共通ルールと違う: …` と書く。
- 共通ルールの設定が `TBD` で、その画面で決める必要があるときは、ユーザーに確認し、答えを共通ルールにも書く。

## 処理の書き方

「5. 初期表示時の処理」と「6. アクション」の各節は、番号付きリストで処理を起きる順に書く。前提・成功時・失敗時の見出しは立てず、分岐も手順の中に書く。

- 1 手順に 1 つの処理。「〜し、〜する」と 2 つ以上つなげない。ただし次の 2 つは 1 手順に書いてよい。
  - 処理と終了: 「〜して終了する。」
  - 条件による分岐: 「◯◯なら〜する。なければ〜する。」（どちらかに「〜して終了する」を含めてもよい）
- 分岐は「◯◯のとき、〜する。」と書く。
- 別の画面へ移る処理の書き方は、下の「遷移」を見る。
- 初期表示時の処理は、画面を開いてから操作できるようになるまでに行う処理（データ取得、URL パラメータの読み取り、初期値の設定など）を書く。
- 状態による表示の切り替え（読み込み中、データなし、エラー、保存中、入力エラーなど）は、独立した節を作らず、その状態になる手順の中に書く。何を表示し、何を隠し、何を非活性にするかを書き、状態が終わる手順で元に戻す（例: 「No.28 を表示する」→ API のレスポンスで「No.28 を非表示にする」）。
- 処理中だけボタンを押せなくする（二重送信の防止）ときは、「No.35〜37 を非活性にする。」と書き、処理が終わる手順に「No.35〜37 の非活性を解除する。」と書く。解除したあとは、画面項目の表の活性条件に従う（「活性にする」とは書かない。活性条件を満たしていない部品まで押せるようになると読めるため）。待機表示（スピナーなど）も同じく、出す手順と消す手順を書く。
- 表示・非表示を切り替える部品は、ワイヤーフレームで番号を振り、「No.28 を表示する」のように番号で書く。番号のないもの（画面全体のスピナーなど）は「フォームの代わりにスピナーを表示する」のように言葉で書く。
- 入力項目を非表示にする手順、編集不可にする手順には、入力済みの値をどうするかを必ず書く（「入力済みの値は残す」か「入力済みの値を消す」）。書かれていないと、実装によって残ったり消えたりするため。API に送るかどうかは、リクエストの表の「値」に書く（「No.18 が「会場」のときだけ送る」）。
- 選択肢を作る・変える処理は、起きるところに書く。画面を開いたときに決まる選択肢（API から取る、権限や状態で増減する）は「5. 初期表示時の処理」に、別の項目の操作で変わる選択肢（都道府県を選ぶと市区町村が変わる）はその操作のアクションに書く。選択肢が変わるとき、選択済みの値をどうするか（残す、未選択に戻す）も書く。
- フォーカスを移す処理のうち、共通ルールのアクセシビリティで決まっているもの（送信時にエラーがあるとき、確認ダイアログを開いたとき・閉じたとき）は、手順に書かない。それ以外にフォーカスを移したいときだけ、手順に「No.9 にフォーカスを移す。」と書く。画面を開いたときのフォーカスは、ここではなく冒頭の表の「初期フォーカス」に書く。
- 処理がない場合は「なし」と 1 行だけ書く。
- 手順にぶら下げる表や段落は、手順の番号の幅だけ字下げする（手順 1〜9 は 3 文字、手順 10 以降は 4 文字）。字下げが足りないと、表が手順の外に出て、番号が 1 に戻って表示される。

### アクション一覧

- 「6. アクション」の最初に、画面のアクションをすべて表で並べる。詳細を読まなくても、この画面で何ができるかがわかるようにするため。
- 「操作」は「「保存」ボタン押下」「「← 一覧へ戻る」リンク押下」「◯◯の選択を変更」のように何をしたときか、「対象」は `No.X`（複数なら `<br>` 区切り。部品のない操作、たとえばブラウザの戻るなら `-`）、「概要」は結果を 1 文で書く。
- ボタンとリンクは、押したときに何かが起きるものすべてについて、アクションを立てる。画面を移るだけのリンクも省かない（遷移先や開き方を書く場所がアクションだけになるため）。
- 一覧は、対象の部品番号の順に並べる（対象が複数あるアクションは、いちばん小さい番号で並べる）。部品のない操作は最後に置く。ID はこの順に `A1` から振る。
- 一覧のあとに、アクションごとに `### A1. 操作` の節を立てて処理を書く。一覧と節の ID・順序はそろえる。

### 遷移

別の画面へ移る処理は、手順に次の形で書く。

- 同じタブで移る: 「SCR-NNN 画面名へ遷移する。」
- 別タブで開く: 「SCR-NNN 画面名を別タブで開く。」
- 設計書のない画面や外部のページは、名前と URL で書く: 「ログイン画面（`/login`）へ遷移する。」「`items[].onlineUrl` を別タブで開く。」
- 遷移先に値を渡すときは、括弧で書く: 「SCR-002 イベント編集へ遷移する（`eventId` に `items[].id` を渡す）。」
- 遷移は、ブラウザの履歴に追加する（ブラウザの戻るで、もとの画面に戻れる）。履歴を置き換えて移るとき（戻るで、もとの画面に戻らせたくないとき）だけ、括弧で書く: 「SCR-002 イベント編集へ遷移する（`eventId` に `id` を渡す。ブラウザの履歴を置き換える）。」
- 遷移の前に確認を出すときは、確認ダイアログを部品にし（「確認ダイアログ」を見る）、もとの操作のアクションでダイアログを表示して、進むボタンのアクションに遷移を書く。

```markdown
### A1. 「← 一覧へ戻る」リンク押下

1. 入力内容に変更がないとき、SCR-001 イベント一覧へ遷移して終了する。
2. No.41 を表示する。

### A11. 離脱の確認で「キャンセル」ボタン押下

1. No.41 を閉じる。

### A12. 離脱の確認で「離れる」ボタン押下

1. SCR-001 イベント一覧へ遷移する。
```

### URL の書き換えと履歴

画面を移らずに、URL のクエリパラメータだけを書き換える手順には、ブラウザの履歴をどうするかを、必ず括弧で書く。書かれていないと、ブラウザの戻るを押したときの動きが実装によって変わるため。

| 書き方 | 意味 |
| --- | --- |
| `（ブラウザの履歴に追加する）` | 書き換える前の URL が履歴に残る。ブラウザの戻るを押すと、書き換える前の状態（前の検索条件、前のページ）に戻る |
| `（ブラウザの履歴を置き換える）` | 今の履歴を書き換える。ブラウザの戻るを押すと、書き換える前の状態は飛ばして、この画面に来る前の画面に戻る |

```markdown
4. URL クエリの `keyword` を No.7 の入力値に、`page` を 1 に書き換える（ブラウザの履歴に追加する）。
```

- 「履歴に追加する」「履歴を置き換える」という言い方だけを使う。ルーターの関数名など、特定のライブラリの名前は書かない。
- 入力するたびに URL を書き換えるような、細かく何度も起きる書き換えは、ふつう「置き換える」にする（戻るを何度も押さないと前の画面に戻れなくなるため）。どちらにするかは設計者が決める。

## バリデーション

入力した値のチェック（バリデーション）は、すべてアクションに書く。入力項目の表には書かない。いつチェックするか、何をエラーにするか、どのメッセージを出すかを、1 か所で読めるようにするため。

### タイミング

いつチェックするかの既定は、共通ルールの react-hook-form のデフォルト設定（`mode` が最初の送信の前、`reValidateMode` が送信してエラーが出たあと）で決まる。項目ごとに違うタイミングにしてもよい（設計者が決める）。skill の側で勝手に決めない。どちらの場合も、実際にチェックするタイミングごとに、次の形でアクションを立てる。共通ルールを読まなくても、設計書だけでタイミングがわかるようにするため。

| タイミング | アクションの見出しの例 |
| --- | --- |
| 入力するたび | `A4. No.29 に入力` |
| フォーカスが外れたとき（blur） | `A2. No.9 からフォーカスが外れる` |
| 選択を変えたとき | `A5. タグの選択を変更` |
| 送信時（submit） | `A6. 「下書き保存」ボタン押下` の手順の 1 つ |

同じ項目を複数のタイミングでチェックしてよい（例: blur でチェックし、submit でもう一度チェックする）。タイミングが決まっていない項目は、アクションを立てずに未決事項に「No.9 のバリデーションはいつ行うか」と残す。

### チェック表

バリデーションの手順には、次の表を付ける。

```markdown
1. バリデーションを行う。

   | No | 項目 | 条件 | メッセージ | 表示先 |
   | --- | --- | --- | --- | --- |
   | 7 | タイトル | 必須 | MSG-001（v1: タイトル） | No.10 |
   | 7 | タイトル | 2 文字以上 | MSG-003（v1: タイトル、v2: 2） | No.10 |
   | 7 | タイトル | 50 文字以内 | MSG-004（v1: タイトル、v2: 50） | No.10 |
   | 7 | タイトル | 使える文字: 全角文字（ひらがな・カタカナ・漢字・英数字・記号）、半角英数字、半角記号 | MSG-005（v1: タイトル） | No.10 |
   | 20 | 定員 | 1〜999 | MSG-009（v1: 定員、v2: 1、v3: 999） | No.30 |
   | 20 | 定員 | 参加者数以上（編集時だけ。`participantCount` より小さいとエラー） | MSG-010（v1: `participantCount`） | No.30 |

2. エラーがあれば、表示先に最初の 1 件を表示して終了する。
```

- 「条件」には、満たすべき条件を、値も含めて書く。値を書く場所はここだけにする。条件の書き方は次の形にそろえる。

  | 条件 | 書き方 |
  | --- | --- |
  | 必須 | `必須` |
  | 文字数 | `2 文字以上`、`50 文字以内` |
  | 使える文字 | `使える文字: ` のあとに、使える文字種を並べる。使えない文字は書かない |
  | 形式 | `メールアドレス形式`、`https:// で始まる URL 形式`、`YYYY-MM-DD` |
  | 値の範囲 | `1〜999`、`今日以降` |
  | 選択数 | `3 つまで` |
  | そのほか（他の項目との関係、API の値との比較など） | 中身を言葉で書く |

- 1 行に 1 つの条件。表の上から順にチェックし、同じ項目で複数違反したときは上の行を優先して表示する。
- 「表示先」には、メッセージを出すエラー表示の部品番号を書く（`No.10`）。画面の部品ではなくトーストなどで出すなら、その出し方を書く（`トースト`）。
- 「メッセージ」は、メッセージ一覧（`messages.md`）の ID で書く。変数のあるメッセージは、括弧ですべての変数の値を指定する（`MSG-004（v1: タイトル、v2: 50）`）。項目名を入れる変数も省略しない。
- 入力可能文字種・入力可能最大文字数で入力できないようにしたものは、チェックしない（違反が起きないため）。たとえば、入力可能最大文字数が `3` の項目に「3 文字以内」の行は書かない。
- 表示していない項目と編集不可の項目はチェックしない。この 2 つは「条件」に書かなくてよい。それ以外に対象外になる条件があれば、「条件」に括弧で書く（例: `参加者数以上（編集時だけ）`）。
- 別のアクションと同じチェックをするときは、表を繰り返さずに参照してよい（例: 「A2・A4 と同じバリデーションを行う。さらに次のバリデーションを行う。」）。

### エラーの表示と消去

チェック表の次の手順に、エラーをどこに、どう出すかを書く。

- 何件出すか（表示先ごとに最初の 1 件、すべて）。どこに出すかは、チェック表の「表示先」で決まる
- 違反がなかったときに、エラー表示を非表示に戻す手順（「なければ No.10 を非表示にする」）。エラー表示の表示・非表示は手順だけで決まるので、省くとエラーが出たままになる
- 送信時のバリデーションなら、エラーがあったときに処理を終了するか、最初のエラー項目までスクロールするか

## API の呼び出し

API は OpenAPI で定義されている前提で書く。設計書に書くパス・パラメータ・ステータスは、OpenAPI の定義と一致させる。定義にないものを書く必要があるときは、未決事項に「API に ◯◯ が必要」と残す。

API を呼ぶ手順は、次の 3 つを 1 組で書く。

1. 手順の文: `` `メソッド パス`（operationId: `xxx`）を呼ぶ。``
2. リクエストの表: 各パラメータにどの値を入れるか
3. レスポンスの表: ステータスごとに何をするか

```markdown
4. 編集のとき、`PUT /events/{eventId}`（operationId: `updateEvent`）を呼ぶ。

   リクエスト

   | 場所 | パラメータ | 値 |
   | --- | --- | --- |
   | path | `eventId` | URL パラメータ `eventId` |
   | body | `title` | No.9 の入力値 |
   | body | `capacity` | No.29 の入力値（数値に変換） |
   | body | `tags` | No.32 で選んだ値の配列（選んでいなければ空の配列） |
   | body | `version` | 初期表示で保持した `version` |

   レスポンス

   | ステータス | 処理 |
   | --- | --- |
   | 200 | MSG-015 をトーストで表示する<br>SCR-001 イベント一覧へ遷移する |
   | 401 | ログイン画面（`/login?redirect=` に現在の URL）へ遷移する |
   | 403 | MSG-020 をトーストで表示する |
   | 404 | MSG-021 をトーストで表示する<br>SCR-001 イベント一覧へ遷移する |
   | 409 | MSG-018 を No.7 に表示する |
   | 422 | `errors[]` を A6 の「422 の表示先」のとおりに表示する<br>最初のエラー項目までスクロールする |
   | 上記以外 | MSG-022 を No.7 に表示する |
```

（例ではリクエストの行を一部省いている。実際の設計書では、OpenAPI で必須のプロパティをすべて書く。全体は [SCR-002 のサンプル](../../../examples/docs/screens/SCR-002_event-edit.md) の A6 を見る）

### API が項目ごとのエラーを返すとき

API が、項目ごとのエラー（422 の `errors[].field` と `errors[].message` など）を返すときは、どのフィールドのエラーをどのエラー表示に出すかの対応表を、その画面で最初にその API を呼ぶ手順のレスポンスの表の下に書く。「対応する項目に表示する」とだけ書くと、エラー表示のない項目のエラーの行き先が決まらないため。

```markdown
   422 の表示先（`errors[]` の 1 件ごとに、`field` に対応する表示先へ `message` を表示する。同じ表示先に複数あるときは最初の 1 件を表示する）

   | `field` | 表示先 |
   | --- | --- |
   | `title` | No.10 |
   | `capacity` | No.30 |
   | 上記以外 | No.7 |
```

- OpenAPI のリクエストのプロパティのうち、エラー表示のある項目に対応するものを 1 行ずつ書く。最後に `上記以外` の行を置き、画面上部のエラー表示などに出す。
- レスポンスの表の 422 の行には「`errors[]` を下の「422 の表示先」のとおりに表示する」と書く。同じ対応を使うほかの手順からは「A6 の「422 の表示先」のとおりに表示する」と参照し、表を繰り返さない。

### 同じ API をもう一度呼ぶとき

同じ画面の中で、同じ API を同じ扱いで呼ぶ手順が複数あるときは、2 回目以降は表を繰り返さず参照してよい。違うところだけを書く。

```markdown
4. 「5. 初期表示時の処理」の手順 4〜6 と同じく `GET /events` を呼ぶ。ただし `page` は固定値 1 にする。
```

リクエストだけ同じでレスポンスの扱いが違うときは、「レスポンスは次のとおり扱う。」と書いてレスポンスの表だけ書く。リクエストの一部だけ違うときは、同じ部分を 1 行にまとめてよい（例: パラメータ欄に `` `title`〜`tags` ``、値の欄に「手順 3 と同じ」）。

### リクエストの表

- 「場所」は OpenAPI の `in` に合わせて `path`、`query`、`header`、`body` のどれか。
- 「パラメータ」は OpenAPI の名前。body の入れ子は `venue.name`、配列は `tags` のように書く。
- 「値」は出どころがわかるように、次のどれかの形で書く。
  - `No.9 の入力値`（変換があるなら括弧で補う: `No.29 の入力値（数値に変換）`）
  - `No.32 で選んだ値の配列`
  - `` URL パラメータ `eventId` ``
  - `固定値 20`
  - `` `GET /me` の `id` ``（別の API の結果）
  - 任意項目で条件によって送らない場合は、括弧で補う: `No.12 の入力値（空なら送らない）`
- OpenAPI の必須パラメータは必ず書く。送ることのない任意パラメータは書かない。
- パラメータがない API は「リクエスト: なし」と 1 行だけ書く。

### レスポンスの表

- OpenAPI でその操作に定義されているステータスを、すべて 1 行ずつ書く。最後に `上記以外` の行を置く（通信エラーもここに含める）。
- 「処理」は、レスポンスのどのフィールドをどこに使うかがわかるように書く（例: `` `items[]` を No.11 に入れて表示する ``）。
- 1 つのステータスで処理が複数あるときは `<br>` で区切り、起きる順に並べる。画面を離れる処理（遷移）は最後に書く。

## 決まっていないこと

- 値が決まっていない欄は `TBD` と書く。
- `TBD` を書いたら、「7. 未決事項」に質問の形で 1 行足す（例: 「タイトルの最大文字数は何文字か」）。
- ワイヤーフレームと会話の内容が食い違ったら、会話の内容を採用し、未決事項に「ワイヤーフレームでは ◯◯ になっている」と残す。ワイヤーフレームの修正は `/write-screen-wireframe` で行う。
- OpenAPI と会話の内容が食い違ったら（パラメータがない、ステータスが足りないなど）、未決事項に「API に ◯◯ が必要」と残す。
