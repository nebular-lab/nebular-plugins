# 画面設計書の記述規則

設計書を誰が書いても同じ形になるように、表記と書き方をそろえる。迷ったらこの規則と [サンプル](../../../examples/docs/screens/) に従い、規則にない判断をしたときはユーザーに伝える。

## 目次

- ファイルと ID
- 番号
- 表記
- 権限
- 画面項目（入力項目 / ボタン / リンク・画面遷移 / テキスト・その他 / 備考に書くこと）
- 処理の書き方
- 入力チェック
- API の呼び出し
- メッセージ
- 決まっていないこと

## ファイルと ID

- ファイル名は `SCR-NNN_<slug>.md`。`NNN` は 3 桁ゼロ埋めの連番、`<slug>` は英小文字とハイフン（例: `SCR-003_order-detail.md`）。
- 画面 ID は一度振ったら変えない。画面を廃止しても ID は再利用しない。
- ダイアログやモーダルも、独立した操作があるなら 1 画面として ID を振る。ワイヤーフレームの描き方は wireframe-rules.md の「モーダルだけの画面」に従う。単なる確認ダイアログ（「削除しますか？」程度）は親画面の部品として描き、親画面のアクションに書く。

## 番号

- 部品の番号（No）は、ワイヤーフレームの `data-no` をそのまま使う。画面項目・アクション・メッセージで共通。設計書の側で付け直さない。
- 振り方の規則（通し番号、順序、モーダルの扱いなど）は [wireframe-rules.md](../../write-screen-wireframe/references/wireframe-rules.md) の「部品番号」に従う。
- アクションは `A1`、`A2`…、メッセージは `M1`、`M2`…と、画面内で連番にする。

## 表記

- 文体は常体で、体言止めか「〜する」で短く書く。「です・ます」は使わない（例: 「一覧画面へ遷移する」）。
- 画面上の文言は「」で囲み、ワイヤーフレームの表記どおりに書く（例: 「保存」ボタン）。
- 他の画面は `SCR-NNN 画面名` で書く。
- API のパス・パラメータ名・レスポンスのフィールド名は `` ` `` で囲む（例: `GET /events`、`eventId`、`items[].title`）。
- 表のセルに複数の内容を書くときは `<br>` で区切る。
- 該当しない欄は `-`、決まっていない欄は `TBD`。空欄は残さない（空欄だと「該当なし」か「書き忘れ」か区別できないため）。
- 該当する部品がない表（入力項目のない画面の「入力項目」など）は、見出しを残し、表を置かずに「なし」とだけ書く。節の中身がない場合も同じ。
- API を呼ばない画面は、冒頭の「API 定義」を `-` にする。

## 権限

- 「閲覧」は `○`（閲覧できる）か `×`（閲覧できない）のどちらか。
- 閲覧できない利用者がアクセスしたときの挙動（ログイン画面へ遷移する、など）は備考に書く。

## 画面項目

部品を次の 4 つに分け、それぞれの表に書く。1 つの部品は 1 つの表にだけ書く。ワイヤーフレームで番号を振った部品は、すべてどれかの表に書く。各表の中は No の昇順に並べる。

| 分類 | 対象 |
| --- | --- |
| 入力項目 | テキスト入力、テキストエリア、数値入力、日付入力、パスワード入力、セレクト、ラジオ、チェックボックス、トグル |
| ボタン | 押すと処理（保存、削除、検索など）が走るボタン |
| リンク・画面遷移 | リンク、および押すと画面を移るだけのボタン（「戻る」「キャンセル」など） |
| テキスト・その他 | 見出し、テキスト、画像、アイコン、一覧、表、タブ、領域（ヘッダーなど） |

処理をしてから遷移するボタン（保存して一覧へ戻る、など）は「ボタン」に書き、遷移はアクションの処理に書く。

### 入力項目

| 列 | 書き方 |
| --- | --- |
| 種類 | 上の「入力項目」の対象から選ぶ |
| 必須 | `○` か `-` |
| 最小文字数 / 最大文字数 | 数字だけ書く（例: `2`、`50`）。制限なしは `-`。セレクトなど文字を入力しない項目は `-` |
| 最大選択数 | チェックボックスなど複数選べる項目だけ数字で書く。それ以外は `-` |
| 使用できる文字種 | 入力を許す文字種を、許すものだけで並べる（`<br>` 区切り）。ここに書いていない文字はすべて使用できない。「◯◯以外」「◯◯を除く」のような禁止の書き方はしない。制限なしは `-`。例: `半角数字`、`半角英数字<br>半角記号`、`全角文字（ひらがな・カタカナ・漢字・英数字・記号）` |
| 初期値 | 画面を開いたときの値。API の値を入れるなら `` `GET /events/{eventId}` の `title` `` のように書く |
| プレースホルダー | 表示する文言を「」で書く。なしは `-` |
| 編集不可条件 | 入力できなくなる条件（例: `status` が `published` のとき）。常に編集できるなら `-` |

### ボタン

| 列 | 書き方 |
| --- | --- |
| 表示条件 | 画面に表示される条件。常に表示なら `常に表示` |
| 活性条件 | 押せる条件。条件を満たさないときは非活性（グレーアウト）で表示する。常に押せるなら `常に活性` |
| 押したときの処理 | アクション ID と概要（例: `A2 イベントを保存する`）。詳細は「5. アクション」に書く |

### リンク・画面遷移

| 列 | 書き方 |
| --- | --- |
| 遷移先 | `SCR-NNN 画面名` か、外部なら URL |
| 開き方 | `同一タブ` か `別タブ` |
| 遷移前の確認 | 確認を出す条件と、出すメッセージ ID（例: `入力内容に変更があるとき M5`）。確認しないなら `-` |
| 表示条件 | 画面に表示される条件。常に表示なら `常に表示` |

### テキスト・その他

| 列 | 書き方 |
| --- | --- |
| 種類 | 見出し、テキスト、画像、アイコン、一覧、表、タブ、領域など |
| 表示内容 | 見出し・ラベル・案内（「条件に合うイベントはありません」など）のような画面の固定文言は「」で直接書く。エラー・確認・完了・お知らせに当たる文は、メッセージ ID（`M3`）で書く。API の値なら `` `GET /events` の `items[].title` `` のように書き、書式は備考に書く |
| 表示条件 | 表示される条件（例: ログイン中のユーザーの `role` が `admin` のとき）。常に表示なら `常に表示` |
| 省略表記 | 長いときに「…」で省略する条件（例: `2 行を超えたら末尾を…`、`30 文字を超えたら…`）。省略しないなら `-` |

### 備考に書くこと

列を用意していない情報は、各表の「備考」に書く。備考に書くのは次の内容に限る。これ以外の情報が必要になったら、列を足すか、この一覧に追加することをユーザーに相談する。書くことがなければ `-`。

| 表 | 備考に書く内容 |
| --- | --- |
| 入力項目 | 形式の制限（メールアドレス形式、`YYYY-MM-DD` など）<br>値の範囲（`1〜999`、`今日以降` など）<br>選択肢の中身と出どころ（固定値か API か）<br>表示条件（常に表示でない場合）<br>入力制限（上限を超えて入力できない、全角→半角の自動変換など、エラーを出さずに入力そのものを制限・変換するもの） |
| ボタン | 文言が条件で変わるとき、その条件と文言<br>二重送信の防止<br>押したあとの待機表示（ローディングなど） |
| リンク・画面遷移 | URL パラメータの引き渡し（例: `eventId` を渡す） |
| テキスト・その他 | 値の表示形式（日付・金額・件数の書式）<br>並び順<br>1 ページあたりの件数とページ送り<br>タブの切り替えで変わる内容 |
| 共通 | 他の部品との関係（例: No.5 を選ぶと表示される）<br>省略表記（「省略表記」の列がない表の部品を…で省略するとき） |

## 処理の書き方

「4. 初期表示時の処理」と「5. アクション」の各節は、番号付きリストで処理を起きる順に書く。前提・成功時・失敗時の見出しは立てず、分岐も手順の中に書く。

- 1 手順に 1 つの処理。「〜し、〜する」と 2 つ以上つなげない。ただし次の 2 つは 1 手順に書いてよい。
  - 処理と終了: 「〜して終了する。」
  - 条件による分岐: 「◯◯なら〜する。なければ〜する。」（どちらかに「〜して終了する」を含めてもよい）
- 分岐は「◯◯のとき、〜する。」と書く。
- 別の画面へ移る場合は「SCR-NNN 画面名へ遷移する」と書く。
- 初期表示時の処理は、画面を開いてから操作できるようになるまでに行う処理（データ取得、URL パラメータの読み取り、初期値の設定など）を書く。
- 状態による表示の切り替え（読み込み中、データなし、エラー、保存中、入力エラーなど）は、独立した節を作らず、その状態になる手順の中に書く。何を表示し、何を隠し、何を非活性にするかを書き、状態が終わる手順で元に戻す（例: 「No.20 を表示する」→ API のレスポンスで「No.20 を非表示にする」）。
- 表示・非表示を切り替える部品は、ワイヤーフレームで番号を振り、「No.20 を表示する」のように番号で書く。番号のないもの（画面全体のスピナーなど）は「フォームの代わりにスピナーを表示する」のように言葉で書く。
- 処理がない場合は「なし」と 1 行だけ書く。

### アクション一覧

- 「5. アクション」の最初に、画面のアクションをすべて表で並べる。詳細を読まなくても、この画面で何ができるかがわかるようにするため。
- 「操作」は「「保存」ボタン押下」「◯◯の選択を変更」のように何をしたときか、「対象」は `No.X`（複数なら `<br>` 区切り。部品のない操作、たとえばブラウザの戻るなら `-`）、「概要」は結果を 1 文で書く。
- 一覧のあとに、アクションごとに `### A1. 操作` の節を立てて処理を書く。一覧と節の ID・順序はそろえる。

## 入力チェック

入力項目の表には「何が正しい値か」（必須、文字数、文字種、備考の形式・範囲など）を書き、アクションには「いつチェックし、違反したらどのメッセージを出すか」を書く。エラーを出さずに入力そのものを制限・変換するもの（入力制限）はチェックではないので、入力項目の表の備考に書く。

### タイミング

いつチェックするかは設計者が項目ごとに決める。skill の側で既定のタイミングは決めない。決まったタイミングごとに、次の形でアクションを立てる。

| タイミング | アクションの見出しの例 |
| --- | --- |
| 入力するたび | `A3. No.13 に入力` |
| フォーカスが外れたとき（blur） | `A1. No.6 からフォーカスが外れる` |
| 選択を変えたとき | `A4. タグの選択を変更` |
| 送信時（submit） | `A5. 「下書き保存」ボタン押下` の手順の 1 つ |

同じ項目を複数のタイミングでチェックしてよい（例: blur でチェックし、submit でもう一度チェックする）。タイミングが決まっていない項目は、アクションを立てずに未決事項に「No.6 の入力チェックはいつ行うか」と残す。

### チェック表

入力チェックの手順には、次の表を付ける。

```markdown
1. 入力チェックを行う。

   | No | 項目 | 条件 | メッセージ |
   | --- | --- | --- | --- |
   | 6 | タイトル | 必須 | M1 |
   | 6 | タイトル | 最小文字数 | M2 |
   | 6 | タイトル | 最大文字数 | M3 |
   | 13 | 定員 | 範囲 | M14 |
   | 13 | 定員 | 参加者数以上（編集時に `participantCount` より小さいとエラー） | M15 |

2. エラーがあれば、各項目の下に最初の 1 件を表示して終了する。
```

- 「条件」には、入力項目の表の列名（`必須`、`最小文字数`、`最大文字数`、`最大選択数`、`使用できる文字種`）か、備考に書いた制約の名前（`形式`、`範囲`）を書く。値そのもの（「51 文字以上」など）は書かない。値は入力項目の表だけに書き、変えるときに 1 か所を直せば済むようにするため。
- 入力項目の表にない条件（他の項目との関係、API の値との比較など）は、「条件」に中身を言葉で書く。
- 1 行に 1 つの条件。表の上から順にチェックし、同じ項目で複数違反したときは上の行を優先して表示する。
- 表示していない項目と編集不可の項目はチェックしない。この 2 つは「条件」に書かなくてよい。それ以外に対象外になる条件があれば、「条件」に括弧で書く（例: `参加者数以上（編集時だけ）`）。
- 別のアクションと同じチェックをするときは、表を繰り返さずに参照してよい（例: 「A1・A3 と同じチェックを行う。さらに次のチェックを行う。」）。

### エラーの表示と消去

チェック表の次の手順に、エラーをどこに、どう出すかを書く。

- どこに出すか（項目の下、画面上部など）と、何件出すか（最初の 1 件、すべて）
- 違反がなかったときに、前に出ていたエラー表示を消すか
- 送信時のチェックなら、エラーがあったときに処理を終了するか、最初のエラー項目までスクロールするか

## API の呼び出し

API は OpenAPI で定義されている前提で書く。設計書に書くパス・パラメータ・ステータスは、OpenAPI の定義と一致させる。定義にないものを書く必要があるときは、未決事項に「API に ◯◯ が必要」と残す。

API を呼ぶ手順は、次の 3 つを 1 組で書く。

1. 手順の文: `` `メソッド パス`（operationId: `xxx`）を呼ぶ。``
2. リクエストの表: 各パラメータにどの値を入れるか
3. レスポンスの表: ステータスごとに何をするか

```markdown
4. 編集のとき、`PUT /events/{eventId}`（operationId: `updateEvent`）を呼ぶ。

   リクエスト

   | 場所 | パラメータ | 値 |
   | --- | --- | --- |
   | path | `eventId` | URL パラメータ `eventId` |
   | body | `title` | No.6 の入力値 |
   | body | `capacity` | No.13 の入力値（数値に変換） |
   | body | `tags` | No.14 で選んだ値の配列（選んでいなければ空の配列） |
   | body | `version` | 初期表示で保持した `version` |

   レスポンス

   | ステータス | 処理 |
   | --- | --- |
   | 200 | M20 を表示する<br>SCR-001 イベント一覧へ遷移する |
   | 401 | ログイン画面（`/login?redirect=` に現在の URL）へ遷移する |
   | 403 | M24 を表示する |
   | 404 | M25 を表示する<br>SCR-001 イベント一覧へ遷移する |
   | 409 | M21 を表示する |
   | 422 | `errors[].field` に対応する項目の下に `errors[].message` を表示する<br>最初のエラー項目までスクロールする |
   | 上記以外 | M26 を表示する |
```

（例ではリクエストの行を一部省いている。実際の設計書では、OpenAPI で必須のプロパティをすべて書く。全体は [SCR-002 のサンプル](../../../examples/docs/screens/SCR-002_event-edit.md) の A6 を見る）

### 同じ API をもう一度呼ぶとき

同じ画面の中で、同じ API を同じ扱いで呼ぶ手順が複数あるときは、2 回目以降は表を繰り返さず参照してよい。違うところだけを書く。

```markdown
4. 「4. 初期表示時の処理」の手順 4〜6 と同じく `GET /events` を呼ぶ。ただし `page` は固定値 1 にする。
```

リクエストだけ同じでレスポンスの扱いが違うときは、「レスポンスは次のとおり扱う。」と書いてレスポンスの表だけ書く。リクエストの一部だけ違うときは、同じ部分を 1 行にまとめてよい（例: パラメータ欄に `` `title`〜`tags` ``、値の欄に「手順 3 と同じ」）。

### リクエストの表

- 「場所」は OpenAPI の `in` に合わせて `path`、`query`、`header`、`body` のどれか。
- 「パラメータ」は OpenAPI の名前。body の入れ子は `venue.name`、配列は `tags` のように書く。
- 「値」は出どころがわかるように、次のどれかの形で書く。
  - `No.3 の入力値`（変換があるなら括弧で補う: `No.7 の入力値（数値に変換）`）
  - `No.9 で選んだ値の配列`
  - `` URL パラメータ `eventId` ``
  - `固定値 20`
  - `` `GET /me` の `id` ``（別の API の結果）
  - 任意項目で条件によって送らない場合は、括弧で補う: `No.3 の入力値（未入力なら送らない）`
- OpenAPI の必須パラメータは必ず書く。送ることのない任意パラメータは書かない。
- パラメータがない API は「リクエスト: なし」と 1 行だけ書く。

### レスポンスの表

- OpenAPI でその操作に定義されているステータスを、すべて 1 行ずつ書く。最後に `上記以外` の行を置く（通信エラーもここに含める）。
- 「処理」は、レスポンスのどのフィールドをどこに使うかがわかるように書く（例: `` `items[]` を No.6 の一覧に表示する ``）。
- 1 つのステータスで処理が複数あるときは `<br>` で区切り、起きる順に並べる。画面を離れる処理（遷移）は最後に書く。

## メッセージ

| 列 | 書き方 |
| --- | --- |
| 種別 | `エラー`、`確認`、`完了`、`お知らせ` |
| 文言 | 画面に出す文言をそのまま。値を差し込む箇所は `{max}` のように書く |
| 表示場所 | `項目の下`、`画面上部`、`トースト`、`確認ダイアログ` など |

- メッセージの表には表示条件を書かない。いつ出るかは、メッセージを参照している箇所でわかるようにする。同じ条件を 2 か所に書くと、片方だけ直されて食い違うため。
  - 入力エラー: アクションのチェック表に、条件と ID を書く
  - 処理の中で出すもの: 初期表示時の処理・アクションの手順やレスポンスの表に「M4 を表示する」と書く。どの手順・ステータスで出るかが表示条件になる
  - 遷移前の確認: リンク・画面遷移の表の「遷移前の確認」列に、条件と ID を書く
  - 部品の表示内容として出すもの: テキスト・その他の表の「表示内容」に ID を書き、「表示条件」列に条件を書く（どの文をメッセージにするかは「テキスト・その他」の「表示内容」の書き方に従う）
- どこからも参照されていないメッセージは置かない。
- 入力項目のエラーは、1 つの条件に 1 つのメッセージ ID を振る（必須・最大文字数・文字種は別の ID）。条件ごとに文言を変えられるようにするため。
- 複数の項目で文言が同じでも、条件が違えば ID を分ける。

## 決まっていないこと
