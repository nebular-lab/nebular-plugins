# /write-screen-spec — 画面設計書の作成（1 画面ずつ）

画面の構成はワイヤーフレームから、API は OpenAPI 定義から、動作は会話から集めて、画面設計書を 1 画面 1 ファイルで書く。設計書は、実装者やレビュアーが画面の構成と動きを把握できるようにするためのもの。見た目はワイヤーフレームに任せ、設計書には「何があり、どう動くか」を書く。

この skill は同じプラグインの `write-screen-wireframe` の規則とファイルも参照する。以下の相対パスは、この skill を読み込んだときに示される Base directory（この SKILL.md があるディレクトリ）を起点にする。

- テンプレート: [assets/template.md](assets/template.md)
- 記述規則: [references/writing-rules.md](references/writing-rules.md)
- 整合性チェックのプロンプト: [references/consistency-check.md](references/consistency-check.md)
- ワイヤーフレームの規則: [../write-screen-wireframe/references/wireframe-rules.md](../write-screen-wireframe/references/wireframe-rules.md)
- 画面一覧の雛形: [../write-screen-wireframe/assets/screens-readme.md](../write-screen-wireframe/assets/screens-readme.md)
- サンプル: [../../examples/docs/](../../examples/docs/)（設計書・ワイヤーフレーム・OpenAPI の書き方に迷ったら見る）

## 引数

`/write-screen-spec [画面 ID・画面名・ファイルパス]`

既存の設計書を直す場合は、画面 ID かファイルパスを受け取る。

## 手順

### 1. 準備

1. 保存先を決める。既定は `docs/screens/`。
   - リポジトリの中に、画面一覧（`README.md`）と `SCR-NNN_*.md` / `SCR-NNN_*.html` が置かれた場所がすでにあれば、そこを使う。
   - どこにもなければ、`docs/screens/` を作ってよいかをユーザーに 1 度だけ確認する。別の場所を指定されたらそこを使う。
   - 以下、決まった場所を「保存先」と呼ぶ。
2. 保存先の `README.md`（画面一覧）を読み、既存の画面 ID と slug、「入力の共通ルール」を確認する。なければ画面一覧の雛形をもとに作る（例の行は消す）。「入力の共通ルール」がない、または雛形のままでまだ誰も確認していなければ、手順 5 で案として示して決めてもらう。
3. 同じ画面の設計書がすでにあれば、新規作成ではなく更新として進める（「番号が変わったときの更新」も見る）。
4. 新規なら、次の連番で ID を振る（`SCR-001` から 3 桁ゼロ埋め）。廃止した画面の ID も含め、一度使った ID は再利用しない。
5. [references/writing-rules.md](references/writing-rules.md) を読む。

### 2. ワイヤーフレームから構成を読む

保存先の `SCR-NNN_<slug>.html` を読む。

- `data-no` の付いた要素を拾い、番号・部品の種類・文言をそのまま設計書の画面項目に使う。番号は付け直さない。
- `data-title` の付いた `.screen` は状態ごとの見た目（読み込み中、データなし、エラーなど）なので、どの処理でその状態になるかを初期表示時の処理とアクションの手順に書く。

ワイヤーフレームがない場合は、先に `/write-screen-wireframe` で作るようユーザーに勧める。ユーザーが設計書だけ先に書きたいと言った場合は、会話で部品を聞き取り、ワイヤーフレームの規則の「部品番号」に従って番号を振る。

### 3. OpenAPI 定義を読む

設計書の処理には、呼ぶ API とそのリクエスト・レスポンスを書く。推測で書くとパラメータ名やステータスが実際の API とずれるので、必ず定義を読んでから書く。

1. OpenAPI 定義を探す。Glob で `**/openapi*.{yaml,yml,json}`、`**/swagger*.{yaml,yml,json}` を探し、見つからなければ `api/`、`docs/api/` などの下も見る。複数あれば、どれを使うかユーザーに確認する。
2. 定義が大きいときは全体を読まず、Grep でこの画面が使いそうなパスや `operationId` を探し、その操作の定義だけを読む。
3. 各操作のパラメータ、リクエストボディ、定義されているステータスを確認する。`$ref` は参照先まで読む。別ファイルへの `$ref`（`./paths/events.yaml#/...` など）もたどる。
4. 設計書の冒頭の「API 定義」に、設計書から見た相対パスでルートの定義ファイルへのリンクを書く。

- プロジェクトに OpenAPI 定義がない場合は、API の部分を `TBD` にして進めてよいか、ユーザーに確認する。
- この画面が API を呼ばない場合は、「API 定義」を `-` にし、処理に API の手順を書かない。

### 4. 案を埋める

会話を始める前に、ワイヤーフレームと OpenAPI から推測できることを、テンプレートの各欄に案として埋める。1 項目ずつ聞くと、入力項目が多い画面では何十往復にもなるため。

- 画面項目: 部品の種類、文言、プレースホルダー、選択肢は、ワイヤーフレームから埋める。必須、文字数、選択肢の値、範囲、形式は、OpenAPI の `required`、`minLength`、`maxLength`、`enum`、`minimum`、`maximum`、`format` から埋める。
- 処理: 画面の目的から、初期表示で呼ぶ API と、各ボタンで呼ぶ API を推測する。リクエストの値はワイヤーフレームの番号と OpenAPI の名前を突き合わせて埋める。レスポンスの表には、定義されているステータスを並べ、処理の案を書く。
- ワイヤーフレームの状態違いの `.screen`（読み込み中、データなし、エラーなど）は、処理の手順に表示・非表示の案として入れる。
- 入力制限: 上限や文字種のある項目は、「入力させない」か「入力させてチェックでエラーにする」かを案として埋める。ワイヤーフレームの `maxlength` などの属性や、既存の画面の決め方があればそれに合わせる。手がかりがなければ、入力させずにチェックでエラーにする案（入力制限 `-`）にし、手順 5 で必ず確認する。
- 推測できないものは `TBD` にする。もっともらしい値を勝手に入れると、決まっていないことが決まったように見えてしまうため。

### 5. 案を見せて直してもらう

埋めた案をユーザーに見せ、違う箇所だけ指摘してもらう。往復は 3〜5 回程度に収める。

1. まず次の 3 つをまとめて見せる。
   - 画面の目的と URL、権限（誰が閲覧できるか、閲覧できない人が開いたらどうなるか）
   - 画面項目の 4 つの表の案
   - 上限や文字種のある入力項目の「入力制限」の案（入力させない制約と、貼り付けなどの細かい振る舞い）。ここはテストの期待値が変わるところなので、1 つずつ確認してもらう
   - 「入力の共通ルール」の案（まだ決まっていない場合だけ）
   - `TBD` の一覧（質問の形で）
2. 次に、初期表示時の処理とアクションの案を見せる。API のリクエストとレスポンスの扱い、状態による表示の切り替えも含める。
3. 入力チェックのタイミング（入力するたび・フォーカスが外れたとき・選択を変えたとき・送信時）は、設計者が決めることなので、案は示しても勝手に決めない。画面全体で共通にするか、項目ごとに変えるかを 1 問で聞き、項目ごとなら表で案を示して直してもらう。

ユーザーが「未定」「あとで」と答えた箇所は `TBD` のままにし、「7. 未決事項」に質問の形で残す。

### 6. 書く

1. [assets/template.md](assets/template.md) をもとに、案とユーザーの修正を反映して書く。見出しの順序と名前は変えない。
2. 保存先の `SCR-NNN_<slug>.md` に保存する。更新日は `date +%F` の値にする。
3. 画面一覧の行を追加（更新時は該当行を更新）する。ワイヤーフレームがまだない画面は、「ワイヤーフレーム」の列を `-` にする。

### 7. 整合性を確かめる

[references/consistency-check.md](references/consistency-check.md) のプロンプトを埋めてサブエージェントに渡し、設計書・ワイヤーフレーム・OpenAPI の食い違いを探させる。返ってきた「エラー」を直し、エラーがなくなるまで繰り返す。ワイヤーフレームの番号自体がおかしい場合は、設計書で合わせ込まず、`/write-screen-wireframe` で直すようユーザーに伝える。

### 8. 報告

次を短く報告する。

- 作成・更新したファイル
- 整合性チェックの結果（残した警告があればその中身）
- 未決事項の件数と中身
- ワイヤーフレームや OpenAPI と会話の内容が食い違っていた箇所（あれば）

コミットはしない。

## 番号が変わったときの更新

ワイヤーフレームに部品を足したり消したりすると、番号が途中に割り込むため、それより後ろの番号がずれる。既存の設計書を更新するときは、次の順に番号を付け替える。

1. 設計書の画面項目の表（項目名・文言）と、ワイヤーフレームの各 `data-no` の部品（文言・種類）を突き合わせ、「旧 No → 新 No」の対応表を作る。新しく増えた部品と、なくなった部品も洗い出す。
2. 対応表をユーザーに見せて確認してもらう。文言が変わった部品など、対応が推測になるものは明示する。
3. 設計書の中の番号をすべて付け替える。画面項目の表の No 列、アクション一覧の「対象」、入力チェック表の No 列、本文の `No.X`（範囲 `No.16〜18` や列挙を含む）が対象。旧番号から新番号への置き換えは一度に行う（順に置き換えると、置き換えたばかりの番号をまた置き換えてしまうため）。
4. 増えた部品を画面項目の表に足し、なくなった部品の行と、それを参照している処理・メッセージを消す。
5. 「7. 整合性を確かめる」を行う。整合性チェックは、番号と部品の中身のずれも探す。
