# /write-screen-spec — 画面設計書の作成（1 画面ずつ）

画面の構成はワイヤーフレームから、API は OpenAPI 定義から、動作は会話から集めて、画面設計書を 1 画面 1 ファイルで書く。設計書は、実装者やレビュアーが画面の構成と動きを把握できるようにするためのもの。見た目はワイヤーフレームに任せ、設計書には「何があり、どう動くか」を書く。

この skill は同じプラグインの `write-screen-wireframe` の規則とファイルも参照する。以下の相対パスは、この skill を読み込んだときに示される Base directory（この SKILL.md があるディレクトリ）を起点にする。

- テンプレート: [assets/template.md](assets/template.md)
- 記述規則: [references/writing-rules.md](references/writing-rules.md)
- 整合性チェックのプロンプト: [references/consistency-check.md](references/consistency-check.md)
- ワイヤーフレームの規則: [../write-screen-wireframe/references/wireframe-rules.md](../write-screen-wireframe/references/wireframe-rules.md)
- 共有ファイルの雛形: [../write-screen-wireframe/assets/shared/](../write-screen-wireframe/assets/shared/)（`overview.md`、`messages.md`）
- 共通ルールの雛形と、項目・選択肢の一覧: [../write-screen-common-rules/assets/common-rules.md](../write-screen-common-rules/assets/common-rules.md)、[../write-screen-common-rules/references/viewpoints.md](../write-screen-common-rules/references/viewpoints.md)
- サンプル: [../../examples/docs/](../../examples/docs/)（設計書・ワイヤーフレーム・OpenAPI の書き方に迷ったら見る）

## 引数

`/write-screen-spec [画面 ID・画面名・ファイルパス]`

既存の設計書を直す場合は、画面 ID かファイルパスを受け取る。

## 手順

### 1. 準備

1. 保存先を決める。既定は `docs/screens/`。
   - リポジトリの中に、概要（`overview.md`）と `SCR-NNN_*.md` / `SCR-NNN_*.html` が置かれた場所がすでにあれば、そこを使う。
   - どこにもなければ、`docs/screens/` を作ってよいかをユーザーに 1 度だけ確認する。別の場所を指定されたらそこを使う。
   - 以下、決まった場所を「保存先」と呼ぶ。
2. 保存先の共有ファイルを読む。なければ雛形から作る（雛形の例の行は消す）。
   - `overview.md`（概要）: ファイルの説明と画面一覧。画面一覧で、既存の画面 ID と slug を確認する。
   - `messages.md`（メッセージ一覧）: 既存のメッセージを把握する。この画面で使えるものがあれば使うため。
   - `common-rules.md`（共通ルール）: 設計書の案を書くときの既定にする。なければ共通ルールの雛形をコピーする。
3. 同じ画面の設計書がすでにあれば、新規作成ではなく更新として進める（「番号が変わったときの更新」も見る）。
4. 新規なら、次の連番で ID を振る（`SCR-001` から 3 桁ゼロ埋め）。廃止した画面の ID も含め、一度使った ID は再利用しない。
5. [references/writing-rules.md](references/writing-rules.md) を読む。

### 2. ワイヤーフレームから構成を読む

保存先の `SCR-NNN_<slug>.html` を読む。

- `data-no` の付いた要素を拾い、番号・タグ名・文言をそのまま設計書の画面項目に使う。番号は付け直さない。タグ名は「タグ」の列に書く（入力項目は中の入力欄。書き方は記述規則の「タグ」）。
- 文言のない部品（`.image`、`.icon` だけのボタン）は、備考に書く読み上げ名の案を作る。
- `data-title` の付いた `.screen` は状態ごとの見た目（読み込み中、データなし、エラーなど）なので、どの処理でその状態になるかを初期表示時の処理とアクションの手順に書く。

ワイヤーフレームがない場合は、先に `/write-screen-wireframe` で作るようユーザーに勧める。ユーザーが設計書だけ先に書きたいと言った場合は、会話で部品を聞き取り、ワイヤーフレームの規則の「部品番号」に従って番号を振る。

### 3. OpenAPI 定義を読む

設計書の処理には、呼ぶ API とそのリクエスト・レスポンスを書く。推測で書くとパラメータ名やステータスが実際の API とずれるので、必ず定義を読んでから書く。

1. OpenAPI 定義を探す。Glob で `**/openapi*.{yaml,yml,json}`、`**/swagger*.{yaml,yml,json}` を探し、見つからなければ `api/`、`docs/api/` などの下も見る。複数あれば、どれを使うかユーザーに確認する。
2. 定義が大きいときは全体を読まず、Grep でこの画面が使いそうなパスや `operationId` を探し、その操作の定義だけを読む。
3. 各操作のパラメータ、リクエストボディ、定義されているステータスを確認する。`$ref` は参照先まで読む。別ファイルへの `$ref`（`./paths/events.yaml#/...` など）もたどる。
4. `overview.md` の冒頭のファイルの表に、API 定義の行がなければ足す（`| [openapi.yaml](../api/openapi.yaml) | API 定義（OpenAPI） |`。パスは `overview.md` から見た相対パス）。設計書の冒頭の表には、API 定義へのリンクを書かない。

- プロジェクトに OpenAPI 定義がない場合は、API の部分を `TBD` にして進めてよいか、ユーザーに確認する。
- この画面が API を呼ばない場合は、処理に API の手順を書かない。

### 4. 案をファイルに書く

会話で 1 項目ずつ聞く前に、ワイヤーフレームと OpenAPI から推測できることを、設計書のファイルに案として書いてしまう。1 項目ずつ聞くと何十往復にもなり、会話に大きな表を出すと読みにくいため。ユーザーにはファイルを読んで指摘してもらう。

1. [assets/template.md](assets/template.md) をもとに、保存先の `SCR-NNN_<slug>.md` を書く。見出しの順序と名前は変えない。更新日は `date +%F` の値にする。
2. 各欄は次のように埋める。
   - 画面項目: タグ、文言、プレースホルダー、選択肢は、ワイヤーフレームから埋める。選択肢の値は OpenAPI の `enum` から埋める。
   - 処理: 画面の目的から、初期表示で呼ぶ API と、各ボタンで呼ぶ API を推測する。リクエストの値はワイヤーフレームの番号と OpenAPI の名前を突き合わせて埋める。レスポンスの表には、定義されているステータスを並べ、処理の案を書く。
   - ワイヤーフレームの状態違いの `.screen`（読み込み中、データなし、エラーなど）は、処理の手順に表示・非表示の案として入れる。
   - 入力可能文字種・入力可能最大文字数: 入力欄が受け付ける範囲を案として埋める。ワイヤーフレームの `type`（`number` など）や `maxlength`、既存の画面の決め方があればそれに合わせる。手がかりがなければ `-`（制限なく入力でき、バリデーションでエラーにする）にする。
   - バリデーション: OpenAPI の `required`、`minLength`、`maxLength`、`enum`、`minimum`、`maximum`、`format` から、チェックする条件の案を作る。タイミングは、共通ルールの react-hook-form のデフォルト設定（`mode`、`reValidateMode`）に従ってアクションを立てる。共通ルールが `TBD` なら、送信時（ボタンのアクション）にまとめて書き、手順 5 で確認する。
   - ボタン・リンク: 押したときに何かが起きるものすべてについて、アクションの案を作る。リンクの遷移先・開き方もアクションに書く。確認ダイアログは部品にし、中のボタンにもアクションを立てる。
   - 共通ルール（`common-rules.md`）で決まっていること（バリデーションのタイミング（react-hook-form の `mode` と `reValidateMode`）、送信中のボタンの非活性、離脱確認、数値のカンマ、一覧の検索条件の復元）は、そのとおりに書く。`TBD` の項目は、設計書も `TBD` にして未決事項に書く。
   - クエリパラメータ: 画面が URL の `?` 以降で受け取るものを、「2. クエリパラメータ」に書く。一覧の検索条件やページを URL に持つかどうかは、共通ルールの「再読み込みやブラウザの戻るで一覧に戻ったときに、検索条件とページを復元するか」に従う。
   - エラー表示: 表示する手順と、非表示に戻す手順を、アクションと初期表示時の処理に書く。
   - メッセージ: この画面で出すメッセージを洗い出し、`messages.md` に同じ意味のものがあればその ID を使う。なければ、変数（`{v1}`、`{v2}`）でまとめられるか（項目名や数値だけが違う文言でないか）を考えたうえで、新しい ID を `messages.md` の末尾に足す。
3. 推測できないものは `TBD` にし、「7. 未決事項」に質問の形で書く。もっともらしい値を勝手に入れると、決まっていないことが決まったように見えてしまうため。推測で埋めたが確認してほしいものも、未決事項に「（案）◯◯ としている。これでよいか」と書く。
4. `overview.md` の「画面一覧」に行を追加（更新時は該当行を更新）する。まだないもの（ワイヤーフレーム、Playwright テスト）の列は `-` にする。

### 5. 読んでもらって直す

ファイルのパスを伝え、読んでもらう。会話には設計書の表を貼らず、次だけを短く伝える。

- 確認してほしい点（未決事項に書いた質問と、推測で埋めた箇所）
- クエリパラメータを書き換える手順で、ブラウザの履歴に追加するか、置き換えるか（ブラウザの戻るで、前の検索条件に戻れるようにするかどうか）。勝手に決めずに聞く
- 冒頭の表の「Enter キーで動くボタン」。入力欄で Enter キーを押したときに動くボタンをどれにするか（何も起きないなら `-`）。ボタンが複数ある画面では、勝手に決めずに聞く
- 入力項目ごとに、「入力させない」（入力可能文字種・入力可能最大文字数）のか「入力させてエラーにする」（バリデーション）のかを決めてほしいこと。テストの期待値が変わるところなので、案のままにしない
- バリデーションのタイミング。共通ルールの `mode`・`reValidateMode` のとおりにしたこと、この画面で違うタイミングにしたい項目がないか。共通ルールが `TBD` なら、どうするかを聞く（設計者が決めることなので、勝手に決めない）
- 共通ルール（`common-rules.md`）のうち、この画面に関わる項目が `TBD` なら、その項目をどうするか。答えは共通ルールにも書く（ほかの観点もまとめて決めたいときは `/write-screen-common-rules` を勧める）
- 共通ルールと違う扱いにした箇所（あれば）
- `messages.md` に足したメッセージと、既存のメッセージを使った箇所。既存のメッセージの文言を変えたい場合は、それを使っている画面を調べて伝える

指摘と答えをファイルに反映する。往復は 3〜5 回程度に収める。ユーザーが「未定」「あとで」と答えた箇所は `TBD` のままにし、未決事項に残す。決まった質問は未決事項から消す。

### 6. 共有ファイルを整える

1. アクションを足したり消したりした場合は、アクション ID を振り直し、設計書の中の参照も直す（「番号が変わったときの更新」を見る）。
2. `messages.md` で、使わなくなったメッセージがあれば、ほかの画面で使われていないことを確かめてから消す（ID は欠番にする）。
3. `overview.md` の「画面一覧」の行が、設計書の画面名・URL と合っていることを確かめる。

### 7. 整合性を確かめる

[references/consistency-check.md](references/consistency-check.md) のプロンプトを埋めてサブエージェントに渡し、設計書・ワイヤーフレーム・OpenAPI の食い違いを探させる。返ってきた「エラー」を直し、もう一度チェックする。チェックは最大 3 回までにし、それでも残ったエラーは報告でユーザーに伝える。ワイヤーフレームの番号自体がおかしい場合は、設計書で合わせ込まず、`/write-screen-wireframe` で直すようユーザーに伝える。

### 8. 報告

次を短く報告する。

- 作成・更新したファイル
- 整合性チェックの結果（残した警告があればその中身）
- 未決事項の件数と中身
- `messages.md` に足したメッセージ・消したメッセージ
- 次に使う skill。遷移（「〜へ遷移する」「〜を別タブで開く」）を足したり変えたりした場合は `/write-screen-flow` で画面遷移図を更新すること、設計書の内容を変えた場合は `/write-screen-playwright-test` でテストを更新すること
- ワイヤーフレームや OpenAPI と会話の内容が食い違っていた箇所（あれば）

コミットはしない。

## 番号が変わったときの更新

### 部品番号

ワイヤーフレームに部品を足したり消したりすると、番号が途中に割り込むため、それより後ろの番号がずれる。既存の設計書を更新するときは、次の順に番号を付け替える。

1. 設計書の画面項目の表（項目名・文言）と、ワイヤーフレームの各 `data-no` の部品（文言・タグ）を突き合わせ、「旧 No → 新 No」の対応表を作る。新しく増えた部品と、なくなった部品も洗い出す。
2. 対応表をユーザーに見せて確認してもらう。文言が変わった部品など、対応が推測になるものは明示する。
3. 設計書の中の番号をすべて付け替える。画面項目の表の No 列、冒頭の表の「初期フォーカス」と「Enter キーで動くボタン」、アクション一覧の「対象」、バリデーションのチェック表の No 列と「表示先」、422 の表示先の表、本文の `No.X`（範囲 `No.35〜37` や列挙を含む）が対象。旧番号から新番号への置き換えは一度に行う（順に置き換えると、置き換えたばかりの番号をまた置き換えてしまうため）。
4. 増えた部品を画面項目の表に足し、なくなった部品の行と、それを参照している処理・メッセージを消す。
5. 「7. 整合性を確かめる」を行う。整合性チェックは、番号と部品の中身のずれも探す。
6. 報告で、画面遷移図（部品番号を ID に使っている）と Playwright テスト（コメントに部品番号がある）の更新が必要なことを伝える。

### アクション ID

アクション ID は、対象の部品番号の順に `A1` から欠番なく振る。アクションを足したり消したりしたとき、または部品番号が変わって並び順が変わったときは、振り直す。

1. 「旧 ID → 新 ID」の対応表を作る。
2. アクション一覧の ID、詳細の節の見出し（`### A6. …`）、本文の参照（`A2・A4 と同じ`、`A6 の手順 8`、表示条件の `A8 で表示し、A9、A10 で閉じる`、`A2、A6、A7 で切り替える` など）をすべて付け替える。置き換えは一度に行う。
3. 手順を足したり消したりして手順番号がずれたときは、その手順を参照している箇所（`手順 4〜6 と同じ`、`A6 の手順 8`）も直す。

アクション ID は設計書の中だけで使う（テスト名や画面遷移図には出ない）ので、ほかのファイルを直す必要はない。
