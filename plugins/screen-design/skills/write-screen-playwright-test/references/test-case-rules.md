# テストケースの作り方

画面設計書とワイヤーフレームから、Playwright のテストケースを洗い出すための決まり。目的は「どのテストケースを作るか」を明確にすること。ここに書くのは考え方だけで、ファイルの構成、補助関数、テスト名、確かめ方の具体例は [サンプル](../../../examples/docs/screens/) のテストコード（画面ごとのフォルダの中の `.spec.ts`）に合わせる。

設計書の書き方は [writing-rules.md](../../write-screen-spec/references/writing-rules.md) で決まっている。設計書に書かれない暗黙の振る舞いもそこにあるので、先に読む。

## 前提

- バックエンドとは通信しない。ブラウザからの API 通信は、すべて [api-mock.ts](../assets/api-mock.ts) でモックする。モックしていない API が呼ばれたら、そのテストは失敗する。
- サーバー側で API を呼ぶ画面と、モックだけでは開けない認証が必要な画面は、対象外。当たるとわかったら、ユーザーに伝えて止まる。
- 画面ごとに、独立した 1 ファイルにし、設計書と同じ、画面ごとのフォルダに置く。ほかの画面のテストと補助を共有しない（共有するのは `api-mock.ts` だけ）。
- テストは実行しない。画面がまだ実装されていなくても使えるようにするため。型チェックと、テスト一覧の出力までを行う。
- 実装の DOM はわからないので、部品は役割と名前（文言）で探す。特定の属性や、ライブラリ固有の DOM の形は前提にしない。アクセシビリティも、名前・説明・フォーカスの位置・キー操作の結果で確かめる。どのライブラリで実装しても、結果が同じなら通るようにするため。
- 前提にしたこと（API の呼び方、部品の見つけ方など）は、テストファイルの先頭のコメントに書く。実装が前提と違ったときは、テストを合わせるのではなく、設計書か実装を直すかをユーザーに相談する。
- 画面の大きさ、タイムゾーン、「今日」は固定する。

## ケースの洗い出し

設計書を上から読み、書かれていることを 1 つずつケースにする。何からどんなケースを作るかは、まず自分で観点を洗い出し、サンプルの作り方と照らして決める。考え方は次のとおり。

- **書かれていることは、すべて確かめる**。初期表示時の処理とアクションの手順、リクエストの表、レスポンスの表の全行（「上記以外」を含む）、バリデーションのチェック表の全行、画面項目の表の条件と表示内容、冒頭の表、クエリパラメータ、閲覧権限（閲覧できる利用者は開けること。閲覧できない利用者が開いたときの動きは、初期表示時の処理に書かれているので、そこから確かめる）。
- **分かれ目は、両側を確かめる**。条件は満たす場合と満たさない場合、数値や文字数は境目のちょうどと 1 つ外、「〜のとき」「なら／なければ」は両方。
- **状態は、なる側と戻る側を確かめる**。表示と非表示、非活性と解除、エラーが出ることと消えること。
- **「起きないこと」は、先に「起きるはずのこと」を待ってから確かめる**。待たずに「出ていない」を見ても、何も確かめたことにならない。実装がなくても通ってしまうケース（最初から出ていないものを「出ていない」と見るだけ、など）は、作らないか、画面で 1 件にまとめる。
- **設計書に書かれていないことは、ケースにしない**。見た目（色、余白）も対象にしない。
- **共通ルール**（`common-rules.md`）のうち、設計書に書かれないもの（入力の扱い、応答を待つ時間の上限、トーストの重なり、ブラウザの戻るでの復元、アクセシビリティ）は、その画面に当てはまるものを、ここでケースにする。設計書に書かれるものは、設計書からケースにする。
- **参照している手順**（「◯◯と同じく」）は、参照先のケースを繰り返さず、違うところだけを確かめる。

1 つのテストで確かめるのは 1 つのケース。似たケースが並ぶときは、ケースの配列を作ってループで生成する（配列がそのままケースの一覧になる）。

## テスト名

テスト名だけを読めば、何を確かめるケースで、設計書のどこから来たかがわかるようにする。

- 先頭に `[...]` で出典（場面、項目、条件など）を付け、続けて条件と期待する結果を 1 文で書く。出典の形は、サンプルに合わせる。
- 設計書の ID（部品番号、メッセージ ID、アクション ID、手順番号、画面 ID）を使わない。項目名、操作名、メッセージの文言、画面名で書く。読む人が設計書を開かなくてもわかるようにするため。
- 画面の中で重複させない。

## 作れないケース

`test.fixme()` で名前だけ置いてよいのは、次の 2 つだけ。理由を名前の後ろに書く。

- `TBD` の欄から作るはずのケース。
- 自動では確かめられないケース（目印のない表示、読み上げソフトでしか確かめられないもの、など）。

「確かめるかどうか決めていない」は理由にならない。設計書に書かれていれば確かめる。

## モックとデータ

- 画面を開く前に、必要な API をすべて登録する。正常系を登録して画面を開く関数を用意し、異常系はテストの中で上書きする。
- レスポンスの形は OpenAPI のスキーマに合わせる。
- 別の画面へ遷移するケースでは、遷移先の画面が呼ぶ API はモックしない。遷移先は URL で確かめ、画面の中身は確かめない。
- メッセージは、`messages.md` の文言を定数にして使う。変数のある文言は関数にする。
